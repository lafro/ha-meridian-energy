# Changelog

Notable changes to Meridian Energy for Home Assistant. Releases from v0.2.6 onwards are listed here; earlier release notes are on the [GitHub releases page](https://github.com/lafro/ha-meridian-energy/releases).

## 0.4.1

### Fixed

- Usage history that is missing is now filled in by the updates after it, so a history that is incomplete no longer stays so: after a setup that imported part of it, after an outage, or for a billing period that started more than 90 days ago. Each grid import and export's history is completed back to midnight 90 days ago, or to midnight at the start of the current billing period when that is older, up to 400 days, as the **Current bill** sensors need every hour from the start of the period: a quarterly period that started 92 days ago now gets its totals. After its own requests, each update asks Meridian for at most 6 more windows of a week for each grid import and export, newest first, each 2 to 5 seconds after the last one ended, and imports each behind the newer hours already stored, with running totals that stay consistent; once the history is complete, it asks for none. The first update after a start of Home Assistant, a reload of the integration or setup asks for none either, so the Meridian entities show as soon as its own requests are done; the update after it asks, knowing the billing period by then. Home Assistant reads what it holds from its statistics at every start, so after a restart the updates go on from where the last ones left off. Two weeks in a row with no readings before the oldest reading, or a week Meridian refuses as before your supply started, are taken as the start of your history, and nothing older is asked for; a shorter gap, as a meter that sent nothing for a week, is asked across, and the readings before it are imported. A day Meridian refuses when asked for alone is taken as the start only when it refuses the day before as well, or has no readings for it; otherwise the day waits and is asked for again, rather than the older history being cut off at it. When a week's last day, or that day's last hour, comes back without readings while the history goes on after it, that day is asked for again with the next one: when Meridian then returns readings for it, the week fails and is asked for again later, rather than that day being left out for good. So is a week's first day, or that day's first hour, with the day before, while the history may go on before it, as for the first hour of a billing period. A window that fails waits an hour, and is then asked for a day at a time, while the older ones go on; a day that keeps failing waits 2 hours, then twice as long each time, up to a day. It never fails the update, whose own data is shown as usual, except when Meridian rejects the session, which asks you to sign in again. The update that imports a grid import or export's first 90 days asks for no more of its history; the next one does, so no week is asked for twice, but for the day 90 days back, whose hours before that import's cutoff it asks for once. When Meridian asks Home Assistant to wait meanwhile, no more history is asked for until that wait has passed, and the next update waits as long, though never less than its usual hour, twice as long each time it comes again in a row; that update asks Meridian for nothing more, not even the billing details. A week whose import Home Assistant did not confirm, or that a reload of the integration interrupted while Home Assistant was saving it, is written again in full, a day at a time, after an hour, after a reload too, and even when it is no longer within the 90 days or the billing period by then; a day Meridian then returns no readings for, or only some of, waits and is asked for again, rather than counted as done. A restart of Home Assistant before then can leave a jump in the running totals where that week ends. Days whose readings an import had to leave out, as when Meridian no longer returns an hour already stored next to them, are asked for again later, with the same waits, rather than counted as done, and so are days still missing an hour for which Meridian returns no readings, although Home Assistant has some stored. What an update learns of days Meridian has nothing for is kept in memory only, so after a restart those days are asked for once more. Until now a gap older than the last 14 days, behind newer stored hours, was never asked for again: updates asked only for the hours after the newest one stored and for the last 14 days.
- An import that reaches back more than 14 days, as setup's or one after a long outage, and that a reload of the integration interrupted while Home Assistant was saving it, is now written again from its oldest hour, as one Home Assistant did not confirm already was.
- An update or a setup that stops part-way now imports what it fetched, newest weeks first, with statistics or without, and whether or not that reaches the newest hour stored. Until now a grid import or export without statistics, as at setup, imported nothing unless it fetched all of its 90 days, and one with statistics imported only when its newer weeks reached the newest hour stored, so a failing older week held back every newer one. The days left are filled in later, by the reconciliation it then owes for the last 14 days and by the updates that complete the history (above).
- Setup now finishes once every grid import and export of a property has imported at least its newest week, and the dialog then says that the rest of the history is still to come: the updates after setup import it in the background. Setup's import now has 4 minutes, as an hourly update has, so no request starts once less than 80 seconds of them remain, and setup stops after 5 minutes, not counting the time Home Assistant takes to save the history, instead of 15: a slow Meridian no longer keeps the dialog open for long. This replaces the option to import only the days already fetched after a failed import, which setup now does on its own.
- When the history import fails because Meridian's service failed or did not answer in time, the setup dialog now also offers to continue without history (**Continue without history**), after the fifth and last attempt too. So it does when a gateway timeout left setup too little of its time for the newest week: setup now says that Meridian did not answer in time, rather than that its time ran out. Setup then removes what the failed import created and creates the entry without asking Meridian for anything more; the entry's first update asks for the last 90 days, as setup would, and the updates after it fill in the rest. It waits as long as a retry would, and the dialog says it is waiting to continue. It is not offered after other failures, such as data Home Assistant could not use or a rate limit, which those updates would most likely meet too.
- The daily reconciliation now also reaches back to hours missing between stored hours of the last 14 days, as when Meridian publishes a day's readings late with no estimates for them first, instead of leaving them to the weekly reconciliation. A gap that started more than 14 days ago is reached back to from 14 days back; its older hours are filled in with the rest of the missing history (above).
- Estimates more than 14 days old are now corrected once a month. On one day of the month for each grid import and export, spread so that not every one asks Meridian on the same day (a grid import and its export may share it), the updates ask Meridian again for every stored day from 90 days back, or the start of the billing period, to 14 days back, 6 weeks at each update, and write again only the hours whose usage or cost Meridian has changed since, or did not have before. When no update ran that day, as when Home Assistant was off, the pass starts at the first update in the 3 days after it. A correction made with **Adjust sum** on any hour from the first to the last hour a week's import writes again, or on the hour after them, is undone, as within the last 14 days, and so it is for the imports that fill in missing days (above); corrections outside those hours are kept. Hours older than 90 days, or than the start of the billing period, are never corrected; a revision made between two passes waits for the next one; a restart before a pass ends leaves the rest of it to the next month, and one on the pass's day or in the 3 days after starts it again. Each pass also checks again where your history starts.

### Changed

- Diagnostics now show for each grid import and export whether its history reaches back as far as the updates complete it (`reaches_target`), which is yes too for one with nothing to complete, as an export register that never exported, no after a start, a reload or setup until the update after the first one has looked, and is not changed by a monthly correction still running or a day whose correction keeps failing, and whether Meridian showed where it starts (`history_start_found`), which a monthly correction checking it again does not change either: yes or no, never a number of days, which would tell how long your history is.
- With debug logging on, each update's summary counts the windows asked for to complete the history and for the monthly correction (`coverage_windows`, `revision_windows`), and their pages are logged with `mode=coverage` or `mode=revision`.
- Rolling back to an earlier version keeps the running totals consistent, but leaves an incomplete history as it is: earlier versions ask only for the hours after the newest one stored and for the last 14 days, so a gap before those stays, and the **Current bill** sensors stay unknown for a billing period with a gap. Let the history fill in first (diagnostics show `reaches_target` for each grid import and export), then roll back.

## 0.4.0

### Fixed

- An import now counts only once Home Assistant has confirmed that it saved it, by reading back where the new hours meet the stored ones. When Home Assistant does not confirm it within about 90 seconds, as while a backup keeps it busy, or what it reads back does not match, that grid import or export fails with a message saying so, and the next update first waits until Home Assistant has saved what it wrote, then writes the same hours again, which repairs anything saved only in part. When Home Assistant saved only the usage or only the cost of an import that reached back more than 14 days, as setup's does or one after a long outage, setup's next try or the next update writes it again from its oldest hour, after a reload of the integration too; a restart of Home Assistant before then can leave some of its hours more than 14 days back with only one of the two for good, and the **Current bill** sensors unknown for a billing period that includes them. Until now an import counted once its writes were queued, so an update could take hours that were never saved for saved ones, and not write them again. In setup, the dialog says that Home Assistant did not confirm that it had saved the statistics, and offers to try again. The time spent waiting for Home Assistant to save and confirm an import does not count towards an update's 4-minute time limit or setup's 15 minutes, so a busy Home Assistant does not leave the other grid imports and exports too little time to fetch their history.
- A change in the registers Meridian returns for a meter, such as one reading replaced by readings per register, no longer fails every update with "invalid electricity data" for up to 14 days. The readings an update fetches for an hour now replace those it had for that hour, so the hour is never counted from both.
- **Current bill usage**, **Current bill cost**, **Current bill export** and **Current bill export credit** now show unknown, with `data_complete` false, when their stored running total does not follow the hourly values, as where an earlier version left it inconsistent: until now they could show a wrong total as complete. They also show unknown for a billing period in which **Adjust sum** was used on their statistic, since such a total can no longer be told from a wrong one; one used on the usage or export statistic makes its cost or credit unknown too.
- The bill totals of each update now wait at most 30 seconds for Home Assistant to finish saving statistics, then read what it has saved, instead of waiting as long as it took.

### Changed

- A correction made with **Adjust sum** in **Settings → Tools → Statistics** in the last 14 days is now undone by the weekly reconciliation too, which writes all of its 14 days again, as every restart or reload of the integration already did; that also writes consistently any running total an earlier version left inconsistent in those days. One made on hours older than those an import writes again is kept, and running totals left inconsistent there are not searched for or repaired.
- An import that finds statistics stored before it but no running total to continue in the 800 days before it, as where those statistics are older than that or were stored without a running total, is refused, with one warning for the statistic besides the usual warning that the grid import or export is failing, and imports nothing, rather than start the running total from zero above them. Hours stored without a running total, as other tools can import them, are passed over when a running total before them is within reach. That grid import or export fails with a message saying that older statistics have no running total to continue, and is tried again later, with the same result until those statistics are deleted in **Settings → Tools → Statistics**; in setup, the dialog says so instead of advising a wait. A first update that fails this way is not tried again after 10 minutes, but with the hourly updates, unless another grid import or export failed in it for another reason, such as Meridian being unavailable: it then fails with that reason, and is tried again after 10 minutes as before.
- Every import, by setup or by an update, now goes through one path, which can also write older history behind hours already stored. Imports into the same statistics take turns, so neither reads the running totals while the other writes them, and after one that Home Assistant did not confirm, the next waits until Home Assistant has saved it. An import's usage and cost are confirmed together.
- Diagnostics give `statistics_write` as the reason a grid import or export last failed when Home Assistant did not confirm its statistics, and `statistics_refused` when the import was refused. Statistics written by this version can be continued by an earlier one: rolling back keeps the running totals consistent.

## 0.3.1

### Fixed

- A gateway timeout on a week of usage history no longer repeats the same request. After the 75-second pause, setup asks for that week's newest day alone. If it comes back, the week's other days follow one at a time, and setup goes back to weeks; a second week that needs this keeps days for the rest of the import. If the day times out too, asking for less does not help, and that grid import or export stops after 2 requests instead of sending more. An hourly update stops at the first gateway timeout and asks for that week by day at its next run, or at the run after if the time limit stops it first; if another week then times out too, or the same one asked for whole again, the updates in the week after that ask for those weeks, and any older ones, by day, rather than ask for them whole again, whether or not the newest week is among them. Until now one timeout led to a resend of the same week, and a second one failed setup. A request sent again after Meridian was briefly unavailable that then times out counts as a gateway timeout too, with the same pause. A week Meridian refuses as too large is now asked for by day instead of failing at once, and so is the rest of that import or update: up to 92 requests for the 90 days instead of 13. A second refusal still fails.
- One property, or one of its grid import and export, no longer stops the others. Each one's newest week is fetched first, then the older weeks, so a property whose supply ended no longer uses up an update's time before the active one is asked for anything. After a gateway timeout, the rest of that property's requests wait out the 75-second pause behind the other properties' requests, so this holds for a property with both grid import and export too, and once the pause has passed, a newest week that waited with them goes before that property's older weeks: a grid export no longer waits behind every week of a grid import whose newest week timed out once. One that fails logs one warning, is tried again after 1 hour, then 2, doubling up to a day, and logs one INFO line when it works again; the others' data shows as usual. Until the first update after a restart or reload has succeeded, each of its retries tries every one again, as its warning says. Until now one failing request made every Meridian entity unavailable and repeated the failing import every hour. Setup now finishes when at least one property imported its history, readings included: a property with no readings in its 90 days, such as one whose supply ended, does not count, so when the other one fails, setup offers to import the days that one fetched, as for that property alone. The others are tried again by the first update after setup, as their warning says, and it warns no second time while they still fail.
- An outage of more than 14 days no longer leaves a gap in the Energy dashboard. Every update now reaches back to the newest hour Home Assistant has stored, up to 90 days, and imports the readings from there in one block. It reaches back to the newest hour with a stored cost too, up to 2 days further, since Meridian may publish an hour's cost after its usage: those hours get their cost as well. An update that stops part-way imports the newer weeks only when they reach that hour; otherwise it imports nothing for that grid import or export and asks again next time. A grid import or export with statistics that stops part-way keeps the newer weeks it fetched, and owes the reconciliation of the rest, which waits 1 hour, then longer, while the hourly updates go on, even when that reconciliation then fails on its newest week; it is owed until it has run. If one of those hourly updates fails, the next waits 1 hour, then longer, counting those failures alone, instead of as long as the reconciliation, up to a day. One whose readings first came after setup, such as an export register that started exporting, and whose import of its 90 days stops part-way, owes that import the same way, and asks for the 90 days again after the wait. While an update keeps finding readings newer than those stored, as when Meridian publishes them more than a week late, the next one searches back again. A property whose supply ended is searched back once; while nothing newer comes, its hourly and daily updates then ask for its newest week alone, one request as before, and its weekly one searches again, with up to 13 requests every week, and the 15-minute time limit, while the property is still listed. Once readings come back in its newest week, that update has the 15 minutes too.
- An update whose statistics could not be saved no longer loses those readings for good: the next update offers them again, instead of taking them for ones already saved.
- The first update after setup no longer repeats what setup just did. It uses the accounts setup found instead of asking Meridian for them again, and continues the imported history with an hourly update instead of reconciling 14 days of it: one request for each grid import or export, instead of 3 and an account list. That includes one whose readings ended more than 14 days ago, and one setup found no readings for in its 90 days, such as that of a property whose supply ended or an export register that never exported: 0.3.0 searched that one's 90 days again, with 13 requests. It knows the estimates setup imported, so **Provisional data intervals** counts them and the next daily update revises them, as after a restart.
- A first update after setup, a restart or a reload that keeps failing because Meridian cannot be reached, does not answer in time or returns unusable data is now retried after 10 minutes, then 30, then hourly, instead of every 10 minutes for good. One that waits for a busy Home Assistant is still retried after 10 minutes. A rate limit now makes hourly updates wait twice as long each time it comes again in a row, up to a day.

### Changed

- When the history import fails or runs out of time part-way through one or more grid imports or exports, after each of them had fetched at least its newest week, the setup dialog now also offers to import only the days each of them fetched (**Import only the days already fetched (at least the last N days)**), N being the days of the one with readings that fetched the fewest. An export register that never exported, or a property whose supply ended, which are fetched last, does not cut the others' history short. It is not offered after a rate limit, which asks for a wait instead; once ticked, it stays ticked for the next tries, after a rate limit too, until you clear it. Setup can then finish. Your older history stays missing until a later version of the integration can fetch it, and the **Current bill** sensors may stay unknown for a billing period that starts before those days. Rolling back to an earlier version keeps that history partial, and so it does after an update that imported only the newer weeks: let the history fill in before rolling back.
- Hourly updates now have a time limit of 4 minutes: no request starts once less than 80 seconds of it remain, and what came back before is imported by the same rules. The grid imports and exports an update did not reach go first at the next one, and still get the reconciliation they missed. An update that reaches back more than 14 days, to import a grid import or export for the first time, such as one setup could not import, or after a long outage, has 15 minutes instead, as setup does: it imports nothing until it is done.
- Diagnostics now show each property's grid import and export: whether it is working, failing or degraded, the reconciliation it still owes, how long it waits before it is tried again (nothing until a first update has succeeded, as each try until then tries every one), how many updates in a row ran out of time before reaching it, and why it last failed (the kind of failure, the error's type, its HTTP status and how long ago).
- With debug logging on, a failed page says when it is followed by the week's days (`probe_1d` or `split_1d`) instead of a resend after a pause, and each update's summary counts the weeks asked for again by day and the grid imports and exports that failed, were degraded or waited. The INFO line of a successful setup counts the weeks asked for again by day and the grid imports and exports that failed, and says whether it imported only recent days.

## 0.3.0

### Fixed

- Requests for usage history no longer ask Meridian for your whole history. Each request now asks for one week at most, by New Zealand date, and every page of it gives both dates. Until now no request had a start date, and later pages had no end date either, so Meridian could have to look through all of your history to answer a request for a few rows. For each property's grid import, and its grid export if it has any, the first setup sends up to 13 requests for its 90 days, and so does a restart after more than 14 days without updates. A restart or the weekly reconciliation sends 3, the daily reconciliation of estimated readings usually 1 (up to 3 once the oldest estimate is more than about a week old), and any other hourly update 1. A meter with more than one register needs up to one more for each extra register for the newest week, at setup and after each restart. A request holds 744 readings at most, one for each register and hour, so a meter with more than four registers needs more than one for every week: two for five to eight registers, three for nine to thirteen. For five registers that is 28 requests at setup and 5 for the weekly reconciliation; for nine, 44 and 7. The newest week is asked for before the number of registers is known, so it may take more requests than the others, but a meter with up to 70 registers is supported. A grid import or export with no readings in the last 90 days, such as that of a property whose supply ended or an export register that never exported, sends 13 at setup, and 13 again at the first update after setup and at each restart or reload, since it cannot be told apart from an account added after setup. The hourly update no longer needs a second request in the morning, when Meridian also returns estimates for the rest of the day.
- A single gateway timeout on a request for usage history no longer fails setup. Setup waits 75 seconds, so Meridian is not asked twice while it may still be working on the first request, then sends that request once more. A request for usage history that fails because Meridian's service is briefly unavailable (HTTP 408, 502, 503 or 520-523), or because of a network error, is sent once more after a few seconds, during setup and in hourly updates. After a gateway timeout, an hourly update still leaves the retry to the next update. Only requests for usage history are sent again; requests for your accounts and billing details behave as before.
- Meridian's rate limit that arrives inside an otherwise successful answer now makes Home Assistant wait an hour, as other rate limits do, instead of reporting unusable data. An answer saying a request was too large still reports unusable data. Its error code is in the warning for a failed setup attempt and, with debug logging on, in the log of hourly updates.
- An update no longer leaves the Energy dashboard's running totals inconsistent when Meridian stops returning readings Home Assistant has already stored. It imports only the hours after a gap where readings are stored, imports nothing for that direction if the newest stored readings are no longer returned, and, when readings come back without a cost Home Assistant already has, imports their usage but leaves the stored cost of those hours, and of the hours before them, as it is. The cost of the hours after them is still written, so hours added since are not left without a cost, however long Home Assistant was off. Each case logs one INFO line, and the next update tries again. Readings whose cost Meridian has not published yet are imported as before, with their cost added once it arrives.
- A week of history that comes back with no readings no longer ends the import when nothing is stored for it: the import goes on, and only two such weeks in a row after a reading are taken as the start of your history, and not even those when readings are stored from before them, as after more than 14 days without updates: the update goes on back to the readings it has stored. Empty weeks before any readings, as for a property whose supply ended some weeks ago or a meter that sent nothing for a while, are not taken as the start either: the import goes on through the 90 days and imports the readings before them, at setup and for an account added later, such as a closed account added through **Reconfigure** to see its history. Meridian's estimates for the rest of today do not count as readings. A week older than every reading that Meridian refuses outright no longer fails setup at once: Meridian is asked for the refused week's days alone, newest first, up to 8 more requests. A refusal of the newest day too, or no readings for it, makes the refused week the start of your history. A day refused after the days after it came back, as when your supply started in the middle of a week and Meridian refuses any request that starts before that, is the start when Meridian also refuses, or has no readings for, the day before it: the days from your supply start are imported. When every day comes back, the week is imported and the import goes on. Readings for the day before a refused day mean the refusal was about something else, so setup fails and is tried again, rather than keep part of your 90 days for good. An error that comes without an error code never counts as such a refusal. Later updates that still ask for those dates, such as the restart and weekly reconciliations in the first weeks after your supply or grid export started, do the same instead of failing. A week refused after Meridian had returned some of its readings, a refusal from the service that renews your login, or a refusal with statistics stored before the dates refused still fails the update, so it can be tried again. When Meridian refuses the newest week and then today alone with an error code, before returning any reading, as it may for a property whose supply has not started yet, such as a new address added to your account before a move, and Home Assistant has no statistics for it, that property has no history yet: nothing is imported for it, one INFO line gives the code, and setup and updates go on for your other properties instead of failing for all of them until the supply starts. Refused there with an HTTP client error, or when statistics are stored for it, however old, the update still fails.
- An initial import that finds no usage history in its 90 days now logs an INFO line saying so, for grid import and for grid export, instead of finishing without a word: at setup, and once again at the first update after setup and after each restart or reload, which search the 90 days again.

### Changed

- The setup dialog's progress now shows how many weeks of history are done. Setup no longer starts a request once less than 80 seconds of its 15-minute limit remain: it stops with the time-limit message, as the limit would have a moment later, and the setup dialog says too little of the time limit was left for another request.
- Requests for usage history start at least a second apart, and go out under the same name as those of MyMeridian's web app.
- If Meridian ever answers a request for a week with readings from after that week, the update fails with the unusable-data message instead of importing them. Readings from before the week asked for are counted and left out, with one INFO line, but the older week must then return them too: if it does not, as when Meridian reads the dates a day early, the update fails the same way, and so it does when two weeks in a row have readings but none for their last day, as when Meridian leaves the end date out. Either would leave one day of every week out of your history for good. It fails the same way when, where two weeks meet, one returns its reading for the hour next to the other and the other does not, twice in a row, as when Meridian leaves out the first hour of the start date or the last hour of the end date: that would leave one hour of every week out.
- Diagnostics now report, for each property and direction, how many days and weeks of history the last update asked for, how many further pages it needed, how many readings came from before their week, and whether it stopped at a gap in stored history. These replace the requested window start and end, which gave a cutoff Home Assistant applied rather than what it asked Meridian for.
- With debug logging on, each page of usage history also says which week it asked for, as days before today, whether that week's first and last hours came back, and, for a failed request, whether it is sent again. Each update's summary counts the weeks that returned readings, came back empty or failed, and the requests sent again. The empty weeks before the start of your history log no page line.

## 0.2.8

### Fixed

- Setup no longer waits without end. An attempt at the history import that is still running after 15 minutes is stopped, the statistics it created are removed, and the setup dialog says the time limit ran out and which request was waiting, then offers to try again as for any other failure.
- A history import that had finished can no longer fail at the last moment because of the billing-period request. Setup no longer asks Meridian for billing details; the first update after setup does, as before, so the **Current bill** sensors fill in then.
- The first update after setup no longer imports the 90-day history a second time when Home Assistant had not yet finished saving what setup imported. That second import could leave one hour with the wrong usage and cost in the Energy dashboard, for good. Setup now waits for its history to be saved, for up to a minute, and closing the dialog while it waits still cancels setup and removes the statistics it created; statistics kept from an earlier installation stay, as when the dialog is closed during the import. The 15-minute limit running out while it waits does not: the import has finished, so setup keeps it. If Home Assistant is still busy after that, for example with a backup, the first update after setup, a restart or a reload waits for it before it reads any statistics: up to 5 minutes, then it tries again 10 minutes later.
- With a MySQL or MariaDB database, setup, and a retry after a failed history import, no longer start before Home Assistant has saved statistics it had to try saving a second time, as it does when the database is busy. Starting then could leave an hour missing from the running totals, or leave part of the failed attempt's history behind. Before it asks you to wait and try again, the setup dialog can now wait up to a minute.
- When Meridian answers a request during the history import with a web page instead of data, and with a status that says it succeeded, the history-import failure form now says it got an unreadable answer, with the HTTP status and the kind of page, instead of naming the internal error behind it (`JSONDecodeError`); an error page is described by its HTTP status, as before. A network failure is described as one.

### Changed

- Requests for usage history now wait up to 75 seconds for Meridian's answer instead of 30. A gateway timeout from Meridian's service has been seen after about a minute, so a slow answer is no longer cut off first and the two can be told apart. Every other request still waits 30 seconds. Making the connection now has a limit of its own, 20 seconds, so a connection that cannot be made is told apart from an answer that does not come.
- When Meridian's service does not answer in time, or answers with a server error (HTTP 408 or 5xx), the setup dialog now says so instead of giving the general message about reaching Meridian: while sending or checking the login code, finding your accounts, importing your history, reauthenticating and in **Reconfigure**. An error answer whose page is cut off, or does not finish arriving in time, is now handled by its HTTP status, as a complete one is, so this holds for it too. The history-import failure form and the integration's error messages also give the HTTP status of such an error. A connection that cannot be made within 20 seconds, and a failure of the Google service that signs in and renews Meridian's login session, still give the message about reaching Meridian.
- With debug logging on, each answer from Meridian logs one line: the kind of request, the HTTP status, the type and size of the answer, which server wrote an error page (Cloudflare, an AWS load balancer, nginx or another), and how long it took. A request that times out or fails logs its error type and how long it waited, and, if Meridian had started to answer, the status and how long the answer took to start. Each page of usage history logs what was asked for and what came back, and a page that fails logs why. These lines contain no account details, addresses, dates or page contents; times are given as hours or days before now.
- The warning for a failed or cancelled setup attempt also gives the median time of its requests, and, with debug logging on, a successful setup logs one line with how long it took, how many requests it sent (session renewals with Google's service included), their median time, and the median time of the usage-history requests alone.
- When finding your accounts, during setup or **Reconfigure**, gets account data Home Assistant cannot use, a warning with the details is now logged; until now it left no trace in the log.
- The README explains how to turn on debug logging before the integration is set up, and that debug logs show how far back your usage history goes: when it is shorter than 90 days, the hour of your first reading. It also says why the Meridian entities can stay unavailable for a few minutes after setup, a restart or a reload while Home Assistant is busy saving statistics.
- The account selection during setup now points to **Reconfigure** for changing it later; it named a **Configure** button the integration does not have.

## 0.2.7

### Fixed

- When the history import during setup fails, the setup dialog now says so instead of spinning forever. It shows what kind of failure it was and which request it happened during or after, and offers to try again with the same login, so no new emailed code is needed. A retry first removes the statistics the failed attempt created and then starts again. Statistics kept from an earlier installation stay, and the retry continues them. Retries wait at least 2 minutes after a failure, or longer if Meridian asks Home Assistant to wait, and setup stops after 5 failed attempts, saying what failed last.
- Setup, and a retry, no longer start importing while Home Assistant is still removing the statistics of a failed attempt, or of an earlier setup that was closed or replaced, or is still saving what a failed attempt added to statistics kept from an earlier installation. The dialog asks you to wait a minute instead, and keeps the accounts you chose. Starting then could leave the new setup with most of its history missing, or with an hour missing from its running totals.
- Pressing Enter again while the setup dialog is still waiting no longer sends a second login code, cancels the history import or starts a second one. The extra press does nothing more, and the dialog moves on to the next step as usual.
- Stopping or restarting Home Assistant during the setup import now removes the statistics it had created and logs one warning about it, as closing the dialog does. Until now Home Assistant cancelled the import only after it had stopped saving data, so those statistics were left behind, and it logged a warning and an error about the unfinished import. If Home Assistant starts to stop while setup is still getting ready to import, the import no longer starts at all.
- Setting up with the same email works again after an earlier setup was left open in a closed browser tab, unless that setup is still importing. Until now that blocked setup as "already in progress" until Home Assistant restarted. History an earlier setup finished importing is kept, and the new setup continues it.

### Changed

- Each failed import attempt logs one warning with the traceback and the last request it made, saying whether that request was still running (`in_flight=yes` or `no`): the kind of request (such as `operation=measurements`), its direction (`CONSUMPTION` for grid import, `GENERATION` for export), the account and property by position (such as `account=1/2`), and the page. It also says whether the statistics that attempt created have been removed (`rollback=removed`) or their removal is still waiting for Home Assistant (`rollback=queued`), which was a separate warning until now. It contains no account details or dates. It replaces the error that 0.2.6 logged for a failed import, and starts with the same words: `Initial Meridian history import failed`.
- Closing the setup dialog during the import, or while the statistics of a failed attempt are being removed, still cancels setup and removes the statistics it created, and now logs one warning once that removal has finished or been queued. The progress text says that closing the dialog cancels the import.
- The connection error message no longer suggests checking your internet connection, because the same error also covers errors returned by Meridian's service.
- Session tokens are left out of the integration's internal text representation of a login, so they cannot reach a log by accident.

## 0.2.6

Requires Home Assistant 2026.10.0 or newer.

### Fixed

- A failed first import now removes the partial statistics it created. The rollback called a recorder-internal function from the wrong thread, so on a real recorder it raised an error, left the partial statistics in place and hid the original failure. It now uses the recorder's public API.

### Changed

- Start-up no longer waits for Meridian. Setup renews the session and loads the account list; the restart reconciliation, which imports statistics, runs in the background after Home Assistant has started. Entities show as unavailable until it finishes. If that first sync fails because Meridian is unreachable or returns unusable data, it is retried after 10 minutes instead of at the next hourly update.
- The **Current bill** sensors no longer have a state class or `last_reset`, so Home Assistant stops recording long-term statistics for them and no longer offers them in the Energy dashboard. The Meridian grid statistics remain the long-term record, and each sensor still shows its billing period as attributes. After updating, Home Assistant shows a repair saying each of these sensors no longer has a state class; delete their old statistics in **Developer tools → Statistics** to clear it.
- Reauthentication uses Home Assistant's reauth-entry helper and unique-ID check.
- Unsupported or incomplete config entries stop at a migration error with a translated explanation instead of an unexplained failure.
- A config entry from a later release with the same major config version loads unchanged, so rolling back to this release does not stop at a migration error.
- The success messages for reauthentication and reconfiguration come from Home Assistant's shared translations.
- The README has automation examples.

### Maintenance

- Tests run against Home Assistant 2026.10 (pytest-homeassistant-custom-component 0.13.370), plus a weekly compatibility run against the newest release and beta.
- Dependabot uses the `uv` ecosystem, so updates change `uv.lock` together with `pyproject.toml`, and CI installs with `uv sync --locked`.
- Development dependencies upgraded; the Pillow and PyJWT overrides were removed because Home Assistant 2026.10 pins patched versions.
- Release notes are this file's section for the version, and CI fails when the version has no section here.
- Workflow checkouts no longer keep the job token, and the release gates install without a dependency cache.
- Snapshot tests cover entity states and diagnostics, and developer notes are in `docs/`.
