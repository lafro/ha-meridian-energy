# Changelog

Notable changes to Meridian Energy for Home Assistant. Releases from v0.2.6 onwards are listed here; earlier release notes are on the [GitHub releases page](https://github.com/lafro/ha-meridian-energy/releases).

## 0.3.0

Requires Home Assistant 2026.10.0 or newer.

### Fixed

- When the history import during setup fails, the setup dialog now says so instead of spinning forever. It shows what kind of failure it was and which request it happened during or after, and offers to try again with the same login, so no new emailed code is needed. A retry first removes the statistics the failed attempt created; statistics kept from an earlier installation stay, and the retry continues them. Retries wait at least 2 minutes after a failure, or longer if Meridian asks Home Assistant to wait, and setup stops after 5 failed attempts, saying what failed last.
- When the import failed because Meridian's service failed or did not answer in time, including when its answers were too slow for any property's newest weeks in setup's 4 minutes, the dialog also offers **Continue without history**, after the last attempt too. Setup then removes what the failed import created and finishes without asking Meridian for anything more; the first update after setup asks for the last 90 days, as setup would, and the updates after it fill in the rest. It is not offered after other failures, such as data Home Assistant could not use or a rate limit, which those updates would most likely meet too.
- Setup no longer waits without end, and no longer needs all of your history at once. The import has 4 minutes: once every grid import and export of a property has its newest week, setup keeps what came back and finishes, and the dialog says that the rest of the history is still to come; the updates after setup import it in the background. With several properties, setup finishes when at least one of them did so and has readings, and the others are tried again by the first update after setup. When not even that came back, the dialog offers to try again, and so it does for an import still running after 5 minutes, not counting the time Home Assistant takes to save it, which setup stops, removing the statistics it created.
- Setup no longer asks Meridian for billing details, so that request can no longer fail an import that had finished. The first update after setup fetches them, as before, and the **Current bill** sensors fill in then.
- The first update after setup no longer imports the 90-day history a second time while Home Assistant is still saving what setup imported, which could leave one hour with the wrong usage and cost in the Energy dashboard for good. Setup waits up to a minute for its history to be saved, and the first update after setup, a restart or a reload waits up to 5 minutes for Home Assistant to save the statistics queued before it, then tries again 10 minutes later. Setup, and a retry, no longer start importing while Home Assistant is still removing the statistics of a failed attempt or of an earlier setup that was closed or replaced, or still saving what a failed attempt added to statistics kept from an earlier installation, as a busy MySQL or MariaDB database can delay it: the dialog asks you to wait a minute instead, and keeps the accounts you chose.
- The first update after setup no longer repeats what setup just did: it uses the accounts setup found, and continues the imported history with one request for each grid import and export instead of reconciling 14 days of it.
- Pressing Enter again while the setup dialog is still waiting no longer sends a second login code, cancels the history import or starts a second one.
- Stopping or restarting Home Assistant during the setup import now removes the statistics it had created, as closing the dialog does, and logs one warning, instead of a warning and an error about an unfinished task.
- Setting up with the same email works again after an earlier setup was left open in a closed browser tab, unless that setup is still importing. History an earlier setup finished importing is kept, and the new setup continues it.
- Requests for usage history no longer ask Meridian for your whole history. Each one asks for one week at most, by New Zealand date, newest first, and every page of it gives both dates. For each property's grid import, and its grid export if it has any, setup sends up to 13 requests for its 90 days; a restart or the weekly reconciliation sends 3, the daily reconciliation of estimates usually 1 (up to 3 once the oldest estimate is more than about a week old), and any other hourly update 1. A meter with more than four registers needs more than one request for each week. A grid import or export with no recent readings, such as that of a property whose supply ended, can send up to 13 after each restart or reload and once a week, and 1 for its other hourly updates. The hourly update no longer needs a second request in the morning, when Meridian also returns estimates for the rest of the day.
- One property, or one of its grid import and export, no longer stops the others. Each one's newest week is fetched first, then the older weeks, and once a property's first newest week comes back empty, as for a supply that ended, the other properties' newest weeks go before its second, so such a property no longer uses up the time of setup or of an update before the active one is asked for anything. One that fails logs one warning, is tried again after 1 hour, then 2, doubling up to a day, and logs one INFO line when it works again, while the others' data shows as usual. Until now one failing request made every Meridian entity unavailable and repeated the failing import every hour.
- A request for usage history that fails because Meridian's service is briefly unavailable (HTTP 408, 502, 503 or 520-523), or because of a network error, is sent once more after a few seconds. After a gateway timeout, no request goes to that property for 75 seconds, so Meridian is not asked twice while it may still be working on the first. Setup then asks for that week's newest day alone: if it comes back, the week's other days follow one at a time; if it times out too, asking for less does not help, and that grid import or export stops after 2 requests. An hourly update stops at the first gateway timeout and asks for that week by day at its next run. A week Meridian refuses as too large is asked for by day instead of failing at once. Requests for your accounts and billing details are not sent again.
- Meridian's rate limit that arrives inside an otherwise successful answer now makes Home Assistant wait an hour, as other rate limits do, instead of reporting unusable data. A rate limit that comes again in a row makes the hourly updates wait twice as long each time, up to a day.
- A first update after setup, a restart or a reload that keeps failing because Meridian cannot be reached, does not answer in time or returns unusable data is now retried after 10 minutes, then 30, then hourly, instead of every 10 minutes for good.
- A property whose supply has not started yet, such as a new address added to your account before a move, no longer fails setup and every update for all of your properties: it has no history yet, and one INFO line says so. A week Meridian refuses because it is before your supply started no longer fails the import either: Meridian is asked for its days alone, and the days from your supply start are imported.
- An outage of more than 14 days no longer leaves a gap in the Energy dashboard. Every update now reaches back to the newest hour Home Assistant has stored, up to 90 days, and to the newest hour with a stored cost, up to 2 days further, since Meridian may publish an hour's cost after its usage.
- Usage history that is missing is now filled in by the updates in the background: after a setup that imported part of it, after an outage, or for a billing period that started more than 90 days ago. Each grid import and export's history is completed back to midnight 90 days ago, or to midnight at the start of the current billing period when that is older, up to 400 days, as the **Current bill** sensors need every hour from the start of the period. After its own requests, each update asks Meridian for at most 6 more weeks for each grid import and export, newest first, a few seconds apart, and none once the history is complete; the first update after a start, a reload or setup asks for none, so the Meridian entities do not wait for them. Two weeks in a row with no readings before the oldest reading, or a week Meridian refuses as before your supply started, mark the start of your history, and nothing older is asked for; a shorter gap, as a meter that sent nothing for a week, is asked across. A week that fails waits an hour and is then asked for a day at a time; a day that keeps failing waits 2 hours, then twice as long each time, up to a day. Until now a gap older than the last 14 days was never asked for again.
- Estimates more than 14 days old are now corrected once a month. On one day of the month for each grid import and export, the updates ask Meridian again for every stored day from 90 days back, or the start of the billing period, to 14 days back, and write again only the hours whose usage or cost Meridian has changed since. Older hours are never corrected.
- The daily reconciliation now also reaches back to hours missing between stored hours of the last 14 days, as when Meridian publishes a day's readings late.
- An import now counts only once Home Assistant has confirmed that it saved it, by reading back where the new hours meet the stored ones. When Home Assistant does not confirm it within about 90 seconds, as while a backup keeps it busy, that grid import or export fails with a message saying so, and the next update first waits until Home Assistant has saved what it wrote, then writes the same hours again, which repairs anything saved only in part. Until now an update could take hours that were never saved for saved ones, and not write them again. A restart of Home Assistant before that retry can leave, for good, some hours more than 14 days back with only their usage or only their cost, or a jump in the running totals where a week filled in later ends.
- An update whose statistics could not be saved no longer loses those readings for good: the next update offers them again.
- An update no longer leaves the Energy dashboard's running totals inconsistent when Meridian stops returning readings Home Assistant has already stored, or returns them without a cost Home Assistant already has: it imports only what it can import safely, logs one INFO line, and tries again next time. Readings whose cost Meridian has not published yet are imported as before, with their cost added once it arrives.
- A change in the registers Meridian returns for a meter, such as one reading replaced by readings per register, no longer fails every update with "invalid electricity data" for up to 14 days.
- **Current bill usage**, **Current bill cost**, **Current bill export** and **Current bill export credit** now show unknown, with `data_complete` false, when their stored running total does not follow the hourly values, as where an earlier version left it inconsistent or where **Adjust sum** was used on their statistic in the billing period: until now they could show a wrong total as complete. Their totals now wait at most 30 seconds for Home Assistant to finish saving statistics, instead of as long as it took.
- An initial import that finds no usage history in its 90 days now logs an INFO line saying so, for grid import and for grid export, instead of finishing without a word.

### Changed

- The setup screens are short: each says what is happening and what to do in a sentence or two, and the detail is in [Limitations and troubleshooting](README.md#limitations-and-troubleshooting).
- Requests for usage history now wait up to 75 seconds for Meridian's answer instead of 30, so a slow answer is no longer cut off before the gateway timeout that Meridian's service has been seen to give after about a minute. Every other request still waits 30 seconds, and making the connection has a limit of its own, 20 seconds. Requests for usage history start at least a second apart, and go out under the same name as those of MyMeridian's web app.
- Hourly updates now have a time limit of 4 minutes: no request starts once less than 80 seconds of it remain, and what came back before is imported. An update that reaches back more than 14 days, as for a first import or after a long outage, has 15 minutes instead. The time Home Assistant takes to save and confirm an import does not count towards either, or towards setup's limits. The grid imports and exports an update did not reach go first at the next one.
- When Meridian's service does not answer in time, or answers with a server error (HTTP 408 or 5xx), the setup dialog now says so instead of giving the general message about reaching Meridian, and the history-import failure form and the integration's error messages give the HTTP status. The connection error message no longer suggests checking your internet connection, because the same error also covers errors returned by Meridian's service.
- Each failed or cancelled setup attempt logs one warning, with the traceback for a failure, saying which request it failed during or after and whether that request was still running: its kind (such as `operation=measurements`), its direction (`CONSUMPTION` for grid import, `GENERATION` for export), the account and property by position (such as `account=1/2`), and the median request time. It also says whether the statistics that attempt created have been removed (`rollback=removed`) or are still being removed (`rollback=queued`). It contains no account details or dates. It replaces the error that 0.2.6 logged for a failed import, and starts with the same words: `Initial Meridian history import failed`. Account data Home Assistant cannot use, found during setup or **Reconfigure**, now logs a warning too.
- With debug logging on, each answer from Meridian logs one line: the kind of request, the HTTP status, the type and size of the answer, which server wrote an error page (Cloudflare, an AWS load balancer, nginx or another), and how long it took. Each page of usage history says which week it asked for, as days before today, and what came back, and each update logs a summary; a successful setup logs one INFO line with its duration and request counts. These lines contain no email, account, address, token, usage, cost or dates: times are given as hours or days before now.
- The README explains how to turn on debug logging before the integration is set up, with the **Logger: Set level** action while the failure form stays open, and that debug logs show how far back your usage history goes.
- If Meridian ever answers a request for a week with readings from after that week, or reads its dates or its first or last hour shifted, that grid import or export fails with the unusable-data message instead of leaving a day or an hour of every week out of your history.
- Diagnostics now show each property's grid import and export: whether it is working, failing or degraded, the reconciliation it still owes, how long it waits before it is tried again, how many updates in a row ran out of time before reaching it, why it last failed (the kind of failure, the error's type, its HTTP status and how long ago), whether its history reaches back as far as the updates complete it (`reaches_target`), and whether Meridian showed where it starts (`history_start_found`), as yes or no, never a number of days. They also report how many days and weeks of history the last update asked for, how many further pages it needed, how many readings came from before their week, and whether it stopped at a gap in stored history, instead of the requested window's start and end.
- A correction made with **Adjust sum** in **Settings → Tools → Statistics** on hours an import writes again is undone: in the last 14 days at every restart or reload of the integration, as before, and now at the weekly reconciliation too, and from the first hour to the hour after the last of each week the updates fill in or correct. One made on other hours is kept. Running totals an earlier version left inconsistent are not searched for or repaired, but those in the hours an import writes again are written consistently.
- An import that finds statistics stored before it but no running total to continue in the 800 days before it, as from another tool or an installation long ago, is refused, with a warning, and imports nothing, rather than start the running total again from zero above them. Setup's dialog, the integration's error message and diagnostics (`statistics_refused`) say so, and trying again gives the same result until those statistics are deleted in **Settings → Tools → Statistics**. Diagnostics give `statistics_write` when Home Assistant did not confirm an import.
- The setup dialog's progress now shows how many weeks of history are done, and says that closing the dialog cancels the import. Closing it still cancels setup and removes the statistics it created, and now logs one warning once that removal has finished or been queued.
- The account selection during setup now points to **Reconfigure** for changing it later; it named a **Configure** button the integration does not have.
- Session tokens are left out of the integration's internal text representation of a login, so they cannot reach a log by accident.
- Rolling back to an earlier version keeps the running totals consistent, but leaves an incomplete history as it is: earlier versions ask only for the hours after the newest one stored and for the last 14 days, so a gap before those stays, and the **Current bill** sensors stay unknown for a billing period with a gap. Let the history fill in first (diagnostics show `reaches_target` for each grid import and export), then roll back.

### Maintenance

- Tests run the integration against a synthetic Meridian service, at the HTTP level and on a real recorder, and check that no log line holds an identifier, a cursor or a date, and that every translation key the code uses exists.
- CI also scans the repository for secrets and checks its content, and the release job waits for the maintainer's approval.

## 0.2.6

Requires Home Assistant 2026.10.0 or newer.

### Fixed

- A failed first import now removes the partial statistics it created. The rollback called a recorder-internal function from the wrong thread, so on a real recorder it raised an error, left the partial statistics in place and hid the original failure. It now uses the recorder's public API.

### Changed

- Start-up no longer waits for Meridian. Setup renews the session and loads the account list; the restart reconciliation, which imports statistics, runs in the background after Home Assistant has started. Entities show as unavailable until it finishes. If that first sync fails because Meridian is unreachable or returns unusable data, it is retried after 10 minutes instead of at the next hourly update.
- The **Current bill** sensors no longer have a state class or `last_reset`, so Home Assistant stops recording long-term statistics for them and no longer offers them in the Energy dashboard. The Meridian grid statistics remain the long-term record, and each sensor still shows its billing period as attributes. After updating, Home Assistant shows a repair saying each of these sensors no longer has a state class; delete their old statistics in **Developer tools → Statistics** to clear it.
- Reauthentication uses Home Assistant's reauth-entry helper and unique-ID check.
- Unsupported or incomplete config entries stop at a migration error with a translated explanation instead of an unexplained failure.
- A config entry from a later release with the same major config version loads unchanged, so rolling back to this release does not stop at a migration error.
- The success messages for reauthentication and reconfiguration come from Home Assistant's shared translations.
- The README has automation examples.

### Maintenance

- Tests run against Home Assistant 2026.10.4 (pytest-homeassistant-custom-component 0.13.375), plus a weekly compatibility run against the newest release and beta.
- Dependabot uses the `uv` ecosystem, so updates change `uv.lock` together with `pyproject.toml`, and CI installs with `uv sync --locked`.
- Development dependencies upgraded; the Pillow and PyJWT overrides were removed because Home Assistant 2026.10 pins patched versions.
- Release notes are this file's section for the version, and CI fails when the version has no section here.
- Workflow checkouts no longer keep the job token, and the release gates install without a dependency cache.
- Snapshot tests cover entity states and diagnostics, and developer notes are in `docs/`.
