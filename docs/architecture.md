# Architecture

## Components

| Module | Role |
|---|---|
| `api.py`, `transport.py`, `graphql.py`, `parsers.py` | Meridian client: emailed-code login, Firebase session renewal, GraphQL queries and response parsing. No external Python requirements. |
| `config_flow.py` | Setup (email, six-digit code, account selection, visible initial import), reauthentication and reconfiguration. |
| `coordinator.py` | `MeridianDataCoordinator`: topology cache, sync-mode selection, measurement fetches window by window for each unit (with resends, the size ladder, pacing and the time budget), the frontier rule, billing metadata and statistics import. |
| `units.py` | What the coordinator remembers about each unit (one direction of one property) between syncs: status, backoff, the reconciliation it owes, its last failure. |
| `lanes.py` | Each unit seen as a history to complete (a lane): its target, the days still missing, the history start, days waiting after a failure, the monthly revision pass, and the windows that fill them in. |
| `windows.py` | Measurement windows: planning, page sizes, the checks on each window's rows, and the stored-aware import rules. |
| `statistics.py` | External statistics: IDs, the one write primitive (`async_replay`: predecessor by time, stored-state fill, suffix shift, write locks, confirmation), billing-period totals and rollback clearing. |
| `sensor.py` | One service device per selected account with diagnostic, provisional-data and current-bill sensors. |
| `diagnostics.py` | Counts, flags and timings only. |

## Setup and start-up

1. The config flow sends a login code to the account email and exchanges it for a renewable session. No password is ever requested or stored; the entry keeps the refresh token and the Firebase user ID.
2. After account selection the flow imports up to 90 days of history while showing progress, then creates the entry. If that import fails, the statistics it created are cleared through the recorder's public API (`get_instance(hass).async_clear_statistics`); statistics that existed before the flow are left alone.
   - A failed import ends the progress step with `async_show_progress_done` and moves to the `import_failed` form, because a progress step cannot abort. The form shows the failure category and the last call, saying whether the failure came during it or after it returned, and a retry keeps the validated session. It describes the failure in words: the HTTP status, `no answer within the time limit`, `an unreadable answer (HTTP 200, html)` for a page that is not JSON, or `a network error (<class>)`. The cause chain it reads (`exception_chain`) is the one a traceback shows, so a context raised `from None`, such as json's internal `StopIteration`, is not part of it. A retry sent before 120 s have passed since the failure (longer if Meridian sent a rate-limit delay) shows the form again with `retry_too_soon` and the seconds left. There are at most 5 attempts in all: the fifth failure ends the flow with `too_many_attempts`, showing what failed, instead of a form whose retry could only abort; after a failure of Meridian's service it shows the `import_failed_last` form instead, which offers only to continue without history (below) and, submitted without it, ends the flow the same way. Its errors are its own (`last_upstream_timeout`, `last_upstream_unavailable`, `_LAST_FAILURE_ERRORS`, and `continue_too_soon` for the wait), since they cannot say to try again. A retry whose repeated rollback the recorder has not finished (a removal whose wait timed out is still pending, even when no rows can be read yet), or that leaves flow-created rows, shows the form again with `cleanup_pending`. With nothing flow-created to remove, because every statistic existed before the flow, the retry still waits for the recorder as the first attempt does (below): rows the failed attempt added to those statistics may still be queued, and a retry that read the history without them could start its window an hour after theirs once an hour had passed, leaving that hour out of every later sum. Either wait has two passes, as the first sync's does (step 4): on MySQL or MariaDB the failed attempt's import can meet a lock error once the recorder catches up and queue itself again, behind the removal or the empty barrier, which then finishes first. The second barrier, queued once the first has run, is behind that second try, so rows it writes back to a flow-created statistic are found by the check that follows (`cleanup_pending`, and the next submission removes them), and rows it adds to a kept statistic are read as its history. Each barrier waits 30 s, once: a timeout in either pass ends the wait, so a first barrier that times out queues no second, and shows `cleanup_pending`. Each attempt builds a new coordinator. A rejected session aborts with `login_expired`.
   - Each attempt runs under a 300 s backstop (`SETUP_IMPORT_TIMEOUT_SECONDS`, an `asyncio.timeout` in `_async_capped_import`); its import has the hourly update's 240 s budget (`SETUP_IMPORT_BUDGET_SECONDS`), so its last request can end before the backstop, and what came back is imported (partial setup, below). When it runs out while the import is running, the attempt raises `SetupTimeLimitError`, is rolled back like any other failure, and the form shows `import_timeout`, saying that the setup time limit ran out and which call was waiting. Its WARNING says `root=SetupTimeLimitError`: the chain behind it ends in the cancellation `asyncio.timeout` stopped the task with, whose class reads like a closed dialog. Any failure's chain is described without such a trailing cancellation, in `cause=`, `root=` and the form's wording alike (`_failure_chain`). Measurements requests have their own 75 s limit (every other call 30 s), above the roughly 60 s after which a gateway 504 has been seen, so a slow answer and a gateway timeout can be told apart. Within that limit, making the connection (a free pooled connection, the name lookup, TCP and TLS) has a limit of its own, 20 s (`CONNECT_TIMEOUT_SECONDS`, aiohttp's `connect`).
   - The setup import uses the accounts the flow found (`topology=`), so it makes no account request of its own, and isolates units as polling does (below): it succeeds when every unit imported at least its newest window in full (`_Unit.imported_newest`: a walk that ended without a failure, or one that stopped after its newest window came back whole and imported what it fetched), or when at least one property's directions all did and one of them found readings (`_Unit.found_readings`; a property with no readings in its 90 days, as one whose supply ended, imported no history, and counted, it would create an entry with none while the active property failed), and the entry's first sync tries the others again, with the deep walk's budget for their initial walks (below). That is partial setup: a walk the budget or a failure stopped part-way has imported its newer windows, and the entry's updates import the rest, through the reconciliation it owes and its lane's coverage (see Lanes). The flow then creates the entry with the `partial` description (`config.create_entry.partial`), which says so, when any unit failed, was degraded or was not reached (`units_failed`, `units_degraded`, `units_deferred`). Otherwise it fails with the failure of the first unit that did not import its newest window, which is what kept it from succeeding: a unit degraded after its newest window did not, and its failure, an older window's unusable data or the time budget, would hide that one, and with it the choice to continue without history after a failure of Meridian's service (below). That is so but for the time budget running out after a walk's size ladder went on past a gateway timeout (`_UnitWalk.gateway_timeout`): the timeout and its 75 s cooldown cost that time, so the attempt fails with that timeout, raised as it came, with its own cause rather than from the budget's error, so that its warning names the transport error, and the form offers to continue without history. It names that unit's failed request (`last_request`) as it was when it failed, rather than the attempt's last request, which may be another unit's: each walk keeps the call it failed at (`_fail_walk`), which is then marked finished, so neither a later failure nor a cancellation names it as still in flight. After a failure of Meridian's service (`upstream_timeout` or `upstream_unavailable`, `_WITHOUT_HISTORY_FAILURES`), the `import_failed` form also offers a `continue_without_history` checkbox. Submitted ticked, it waits as long as a retry does, saying so with `continue_too_soon` rather than the retry's `retry_too_soon`, as the last failure's form does, repeats and checks the rollback as before a retry (`cleanup_pending` while the recorder is behind; a flow removed meanwhile aborts), then creates the entry with the `partial` description and no import: it hands the entry the accounts (`SetupHandoff.imported` false), so the entry's setup makes no request and its first sync imports the history as a new one does, keeping what it fetched, and the oldest hour of any deep replay a failed attempt left unconfirmed in statistics that existed before the flow (`SyncMemory.unconfirmed` alone), so its walks reach back to it as a retry's would. After any other failure (data it could not use, a rate limit, a connection not made) the entry's updates would most likely fail the same way, with no form to say why, so the form offers the retry alone. A rollback to an earlier release keeps a partial history partial: earlier releases ask only for the hours after the newest one stored and for the last 14 days, so a gap before those stays.
   - The setup import (`async_fetch_and_import(setup_import=True)`) leaves out billing metadata and bill totals: its coordinator is discarded, and the entry's first sync fetches them. Each replay in the import has confirmed its own writes before it returned (Statistics, below); one the recorder did not confirm fails its unit with `statistics_write`, which the form shows as `import_statistics_write`, describing the failure as Home Assistant not confirming that it had saved the statistics. One that refused to write, with no running total in reach to continue, fails it with `statistics_refused`, which the form shows as `import_statistics_refused`: it says what is wrong with the stored statistics, and does not advise a wait. After the import the flow still calls `async_confirm_visible`, a check that costs little: one barrier (an empty `async_clear_statistics` with `on_done`, as below, 30 s) behind whatever the recorder still has queued, then a read-back of the newest row written to each energy statistic. When the barrier timed out or a row is missing, it runs one more barrier, and reads back again: the recorder may catch up a moment later, and an import it had to retry has queued itself again behind the first barrier (step 4). A second timeout, a second mismatch or a failed read is logged at INFO and setup continues. The wait sits inside the time limit and the rollback, so closing the dialog during it still rolls the import back. The time limit running out during it ends only the wait, as the wait's own timeout would (INFO, `saved=no`): the import has finished, and rolling it back would remove a complete history because the recorder was busy, with the removal queued behind the same busy recorder. So the whole wait can reach 60 s; the INFO line for a timeout gives the time it waited in all. The entry's first sync waits for the recorder again (step 4), so setup giving up does not let it import over rows still to be saved, short of rows the recorder retried twice in a row.
   - A gateway timeout (HTTP 504, 524, or no answer in time) or a service error (408, other 5xx) raises `MeridianUpstreamError`, a `MeridianConnectionError` subclass, and the form shows `upstream_timeout` or `upstream_unavailable`; polling and entry setup use the same keys, and so do the steps before the import (sending and checking the login code, account discovery), reauthentication and reconfiguration (`_connection_error_key`). The status reaches the user through the failure form's description and the exceptions' messages (`{detail}`); the two error strings have no placeholder, because the failure form already gives the detail, so the other forms do not show the status. Only Meridian's own services count: a connection not made within its 20 s limit (aiohttp's `ConnectionTimeoutError`, almost always a local network problem; aiohttp raises it only for that limit, and a request's total limit running out while it connects raises a plain `TimeoutError`), and any failure of Google's session service (Firebase), which the login uses, stay plain connection errors (`cannot_connect`). A successful attempt logs one INFO line with its duration, request count, direction count, median request time, median measurements request time, the counts of windows that returned readings, came back empty or failed (`windows_ok`, `windows_empty`, `windows_failed`), the number of resent requests (`retries`), the windows asked for again by their days (`splits`), whether the start of the history was found (`history_start`), the units that failed while another property imported (`units_failed`), whether some of the history was left for the entry's updates (`partial`) and whether the read-back succeeded (`saved`). Requests are counted where they are sent: a client call can send several (a session refresh, a retry with a new token, one `account` request per account), so the coordinator opens a `count_requests()` tally for each sync, which the transport adds every request to, with its time, for that sync's task alone.
   - The flow handles one submission at a time (`_async_submit`). The frontend sends one for each press of Enter, even while an earlier one is waiting, and the flow API accepts any number. A submission that arrives while an earlier one still waits on Meridian or the recorder makes no request and changes nothing: it waits for the earlier one (through `asyncio.shield`, so its own cancellation leaves that one alone), then gets the step the flow is at, or the same abort. Both answers must carry the real next step: the dialog replaces its form element with each answer it handles, so it shows whichever answer arrives first and drops the other, and an earlier form shown again could not be submitted to a flow that had moved on (Home Assistant would reject it with HTTP 400). So a second email sends no second code, only one attempt starts at a time, a late answer cannot replace the login data an import is filling in, and no form or abort reaches Home Assistant while the import runs, which would make it cancel the progress task. An `AbortFlow` raised while handling a submission (by Home Assistant's unique-ID checks, say) propagates as usual, and a submission that waited for it raises the same exception, so Home Assistant turns both into the same abort, with the same reason, placeholders and translation domain. When the handled submission created the entry, as continuing without history does, Home Assistant still adds and sets up the entry before the flow ends, and the flow is at its earlier form until then: the waiting submission answers only once Home Assistant has removed the flow (`async_remove`), with an `already_configured` abort, which reaches the dialog second and is dropped. A copy of the entry's result would make Home Assistant create a second entry with the same unique ID and replace the first. So does a submission that arrives once the entry is created, while Home Assistant still sets it up, as Enter pressed again, or the finish step asked for again (`_created`, `_answer_after_entry`): handled, it would repeat the rollback under the new entry's first update and create that second entry.
   - Before the first attempt the flow waits for the recorder to finish the work queued so far, including a task it is already running, in two passes of up to 30 s each. It queues a removal of no statistics (`get_instance(hass).async_clear_statistics([], on_done=...)`) and waits for its callback; the recorder runs its tasks one at a time and in order. The second pass queues another once the first has run, so work the recorder queued again behind the first (step 4) is done too. The recorder's commit future would not do, because it is `None` whenever the queue is empty, as it is while the recorder runs the last task it took off it. So a removal that an earlier setup of the same accounts left queued or running (closed, failed or replaced) has finished before existing statistics are read. Read earlier, those rows would count as existing history and the new import would only continue them, before the queued removal deleted them. If the wait times out, the form shows `cleanup_pending`. Submitting that form only waits again: for a single account found at login (the `discovery_retry` form), the flow does not ask Meridian for the accounts a second time, and the `accounts` form comes back with the submitted selection as its default, because the frontend fills a form from its defaults.
   - Before each API call the coordinator records a `RequestContext` (operation, direction, account and property positions, window `k/n`, page, bound — `dates` for a window's first page, `before` for a later one — and call count) with no identifiers, and marks it finished when the call returns, so a later failure (writing statistics, say) is not blamed on that call. The flow copies it, and the median time of the attempt's HTTP requests, when the attempt ends, and logs one WARNING with the traceback per failed attempt (`in_flight=yes|no`, `median_request`). Its `root` is the innermost error of the chain a traceback shows (`_failure_chain`), so a suppressed context (`raise ... from None`) is left out, and so is the `CancelledError` that a time limit raises its `TimeoutError` from; the setup time limit names itself (above), and a network error is named by the library class its transport error records. Its `rollback=removed|queued` says whether the rollback's removal finished within its 30 s wait. The removal itself logs nothing, so a queued removal is reported once: in this WARNING, in a cancellation WARNING (below), or, for a retry, as `cleanup_pending` on the form. Its `request_elapsed` and `total_elapsed` end when the import ended, before the rollback, which can wait 30 s on a busy recorder; the cancellation WARNING times the same way.
   - Closing the dialog cancels the import task. So does Home Assistant stopping: while an attempt runs, the flow listens for `EVENT_HOMEASSISTANT_STOP` and cancels the task then, while the recorder still runs, so the rollback's removal is queued before the recorder's final write. Home Assistant itself cancels a task still running at shutdown only after the recorder has stopped, so that removal would never run, and it logs a warning and an error about the task. The rollback runs, then the task logs one WARNING: whether the import had returned (setup was then waiting for Home Assistant to save it, not for Meridian), whether the dialog was closed, Home Assistant is stopping, or the task was cancelled with the dialog still open, and whether the removal finished or is still queued. A cancellation that interrupts a failed attempt's rollback logs that failure, with its traceback, in the same WARNING, because the flow never logs a cancelled attempt: closing the dialog removes the flow, and otherwise (Home Assistant stopping removes no flow) the flow sees only the cancellation, so its form says the import was cancelled. The flow does not log a cancellation a second time. No attempt starts once Home Assistant is stopping (`hass.is_stopping`), as when a submission's wait on the recorder ends after the stop event: nothing would cancel that attempt, and it would hold up the shutdown and outlive the recorder, so the flow aborts with `login_expired` instead, even while the recorder is still behind. Nor does one start in a flow removed during that wait. A retry's wait is its repeated rollback, and no attempt runs then to log the end of setup, so the flow logs one WARNING once that removal has finished or timed out: that Home Assistant is stopping, or that the flow was removed (the dialog was closed, or a new setup for the same email replaced the flow at its form, which the flow cannot tell apart), and whether the removal finished or is still queued. The failed attempt's own WARNING has its failure and traceback.
   - A new setup for the same email aborts earlier user-started flows for it that wait at a form (`user` after a failed send, `otp`, `discovery_retry`, `accounts`, `import_failed`, `import_failed_last`) or whose import ended with nobody fetching the next step (progress done to `finish` or `import_failed`), such as one left in a closed browser tab, which Home Assistant does not list and which would otherwise block the email with `already_in_progress`. Statistics a successful import wrote are kept, and the new setup continues them as existing history. A running import is left alone. An email that is already configured is refused first, before any flow is touched. That keeps two kinds of flow out of reach, both of which have an entry: a reauthentication, which runs only while its entry exists (Home Assistant aborts it when the entry is removed or reloaded), and a setup whose new entry is still being set up, because Home Assistant adds the entry and then waits for its setup with the flow still in progress (at progress done to `finish`). A reconfiguration carries no unique ID, so it is never found. A flow removed while a step is still waiting on Meridian or the recorder never starts an import.
3. `async_setup_entry` only renews the session and caches the account topology (`async_prepare_topology`). A rejected session raises `ConfigEntryAuthFailed` (reauthentication); an unreachable Meridian, a rate limit or unusable data raises `ConfigEntryNotReady` (Home Assistant retries). Right after the flow, it makes no request at all, and leaves renewing the session to the first sync: the flow's `finish` step leaves a `SetupHandoff` in `hass.data[DOMAIN]["setup_handoff"]`, keyed by the email, which `async_setup_entry` takes once. It holds the accounts the flow found, when its import's sync started, and what the import's coordinator remembered of each direction (`SyncMemory`, a copy taken once the attempt succeeded, so after no rollback): each unit's state, the measurement cache and the rows an hour holds. The coordinator caches those accounts as of that time, and counts the setup import as its last reconciliation (`reconciled_at`), so its first sync runs in the mode the cadence asks for, normally `tip`, for every direction with statistics, instead of a 14-day `restart`: one request per direction instead of 3 and the account list. That holds for a direction whose readings ended more than 14 days ago too, which would otherwise run a new 90-day `initial`: the frontier rule reaches back to its newest stored hour, and setup's walk found nothing newer, so it is quiet (below). With setup's measurement cache, the provisional rows setup imported are counted as after a 14-day restart, and the first daily reconciliation reaches back to the oldest of them. With setup's unit states, a unit that failed in setup, which the first sync tries again, logs no second warning while it still fails, and one INFO line once it works. A direction without statistics, such as one that failed at setup, still runs `initial`. Read late, after a failed first setup of the entry, the handoff is still safe: the accounts are refreshed a day after setup, the reconciliations fall due counted from the setup import, and the cache holds what setup stored. After setup went on without history (`SetupHandoff.imported` false) there is no import to continue, so `reconciled_at` is not set: a direction with statistics kept from an earlier installation runs the 14-day `restart`, and one without runs `initial`. Nothing is stored: a restart or reload starts as before, but for the oldest hour of a deep replay that was not confirmed, and the dates whose coverage import was not confirmed, which an entry keeps across its reloads (Statistics, step 5; Lanes).
4. The first sync runs as an entry background task once Home Assistant has started. Entities exist from the cached topology but are unavailable until it finishes. It asks for no older history (`_covers`; see Lanes), so they do not wait for that: the update after it does, with the billing period this sync fetched. Before any request or statistics read, it waits for the recorder to save the work queued before it (`async_wait_for_recorder` with `passes=2`, up to 10 barriers of 30 s each in all), such as setup's import or the rows of the entry's coordinator before a reload. Read earlier, it would find no history, choose `initial`, start the running sums from zero again and queue that import behind the unsaved rows: when an hour boundary passed between the two, the stored sum then broke at that hour for good. It waits in two passes, the second barrier queued once the first has run. On MySQL or MariaDB, an import that meets a lock error (errors 1205, 1206 and 1213: a lock-wait timeout, too many locks, a deadlock) is queued again at the back of the recorder's queue (`ImportStatisticsTask` re-queues itself when `import_statistics` returns `False`), behind a barrier queued before it ran, which then completes with those rows unsaved; the second barrier is behind that retry. An import retried twice in a row can still be saved after the sync reads. SQLite never retries. The sync's duration (`sync_duration_seconds` in diagnostics, `duration=` in its debug summary) is timed from the end of that wait, so a busy recorder does not read as a slow Meridian sync. While the recorder is still behind, the sync fails with `recorder_busy`, retried after 10 minutes. A first sync that fails for connection, data or time-budget reasons, or because Home Assistant did not confirm the statistics it wrote (`statistics_write`), is retried after 10 minutes, then 30, then hourly (`FIRST_SYNC_RETRY_SCHEDULE`); one whose replay was refused (`statistics_refused`) waits for the hourly update, since no retry clears it; Home Assistant honours `retry_after` because the first sync is an `async_refresh`. A rate limit uses Meridian's `retry_after`, doubled for each rate limit in a row, up to a day. The setup import itself does not wait here, because the flow has just waited, in two passes too, before starting each attempt.

## Sync modes

The coordinator polls hourly and picks a mode for each fetch:

| Mode | When | Cutoff | Windows sent (NZ dates, newest first) |
|---|---|---|---|
| `initial` | A property or direction has no statistics yet (or they are more than 14 days old at start-up) | 90 days | 13: 91 dates |
| `restart` | First sync after Home Assistant starts, when statistics exist | 14 days | 3: two weeks and the cutoff's date |
| `full_reconciliation` | Every 7 days | 14 days, the provisional-data correction window | 3 |
| `targeted_reconciliation` | Daily | From 6 hours before the oldest provisional interval or the oldest hour missing between stored hours; at least 48 hours, at most 14 days | 1 to 3 |
| `tip` | Otherwise | The last 24 hours | 1: yesterday and today |

Topology and billing metadata are cached for a day.

**The frontier rule.** Every mode's cutoff reaches back to the frontier too, the newest stored energy hour, up to 90 days: `since = max(now − 90 d, min(mode's cutoff, frontier))` (`_requested_since`). The frontier is read from the recorder once per coordinator (`async_latest_numeric_statistic_start`: the newest row with a running sum, looked up by time when newer rows have none) and moved on after each import whose replay was confirmed. Meridian may publish an hour's cost after its usage, so the cost statistic's newest stored hour can lag the energy frontier: a cutoff the rule moves back reaches back to that hour too, at most 48 h before the energy frontier (`COST_LAG_MARGIN`), so a cost statistic that stopped for good does not make such walks longer still. The cost frontier is read once in the same way and moved on to the newest hour whose cost an import wrote (`_note_imported`). Without it, the hours between the two kept no cost row for good after such an outage: the cutoff dropped them, and no later reconciliation reached back that far. So after an outage longer than a mode's span, without a restart, the walk still joins the new rows to the stored history: without it, a 20-day outage left 6 days missing for good, since the weekly reconciliation reaches back 14. A cutoff older than 14 days is beyond what the measurement cache compares (its own 14-day cutoff), so such a walk's rows are imported as one replay from the oldest hour fetched, as an initial import's are. After such a replay that was not confirmed, every walk of the unit, whatever its mode, reaches back to the oldest hour it wrote, beyond the 90 days too (see Statistics, step 5). A walk that stops short of the frontier still imports the windows it fetched (see Import rules): the frontier then moves on to its newest hour, and the days between are left to the reconciliation the unit owes and to its lane's coverage (see Lanes).

A direction whose readings stopped, as for a supply that ended, never moves its frontier, so the rule alone would walk every hourly update back to it, up to 13 requests an hour for nothing. So a walk that ended without a failure and found no reading newer than the frontier it started from (`_Unit.frontier`: by the time the unit is settled, its import has moved the frontier on to its newest hour) makes the unit quiet at the frontier it leaves (`UnitState.quiet_frontier`, `_note_quiet`). A first import has no frontier to start from: it leaves the unit quiet only when its newest window had no readings, as for a supply that ended, so the entry's first update after setup asks for that window alone (`_Unit.found_new`). While the frontier is unchanged and older than the mode's own span, the hourly and daily updates of a quiet unit stop at an empty window before any reading, with no stored hour inside it (`_quiet`, `_take_window`): one request, as before the rule. Once readings come back in its newest window, the walk goes on to the frontier as before, with the 900 s budget of a deep walk when the frontier is more than 14 days back (below), and the import moves it on; a walk that finds any reading newer than the frontier it started from ends the quiet state, imported or not. So readings Meridian publishes more than a week late, for days older than the newest window, are fetched at every update until a walk finds nothing newer: counted against the frontier the import had moved, every walk that imported looked quiet, and the next updates stopped at the empty newest window until the weekly reconciliation. The weekly reconciliation, a restart and an initial import walk back in full, for readings that come back for older days only: up to 13 requests a week for such a direction, with the 900 s budget, for as long as its property is listed. A quiet walk that stops at its empty newest window imports nothing; one whose readings came back imports what it fetched.

## Measurement windows

Every measurements request asks for one window of whole New Zealand dates, `startOn` to `endOn`, both included, at most 7 days long (`windows.plan_windows`). The newest window ends on today's NZ date, each older one ends the day before the next newer one starts, and the oldest starts on the NZ date of the first hour kept, the first whole hour from the mode's cutoff (`windows.first_date`). That is the cutoff's own date, except in the hour before NZ midnight: in the hour after NZ midnight, from the September change until about late December, 90 days back is 23:30 in standard time, and no row of that date is kept, so the windows start on the next and the 90 days still take 13. A window's rows run from NZ midnight at the start of `startOn` to NZ midnight after `endOn`: 167 to 169 hours for a week across a daylight-saving change. Rows before the cutoff and rows not yet over are left out, as before.

- **The request.** The query (`graphql.measurements_query`) declares `$last: Int!`, `$startOn: Date!` and `$endOn: Date!`, so a request that left out a bound would fail validation instead of asking for the whole history. Every page of a window sends the same `startOn`, `endOn` and `last`; a continuation page adds only `before`, the start cursor of the same window's previous page, so no cursor crosses windows or modes. It never sends `startAt`/`endAt` or asks for `totalCount`/`edgeCount`. It goes out under the web app's operation name, `GetMeasurements`, with `?opName=GetMeasurements` on the URL; `graphql.MEASUREMENTS_WEB_APP_NAME` switches both back to `measurements` on the bare URL together.
- **Page size.** `last = min(744, max(24, ceil(hours × rows per hour × 1.25) + 4))`: 214 for a week, 64 for the hourly update's two dates. The rows an hour holds (one per meter channel) are learned from the first window of a walk that returns readings, so a meter with two to four channels needs more pages on that window only, one more for each extra channel at most. A week of five channels or more holds 840 rows or more, over the 744 cap, so every week takes one page for each 744 rows it holds: two for five to eight channels, three for nine to thirteen. A 90-day walk sends 28 requests for five channels, 44 for nine, 77 for 21. A window may take 16 pages of 744 rows, or as many smaller pages as 11,904 rows need (`windows.page_limit`), so the newest week, in pages of 214 rows, takes 17 for 21 channels; a week of up to 70 channels fits.
- **Each window's rows** (`windows.WindowRows`) are kept apart until the window is complete, then joined to the direction's, so a failed window leaves nothing behind. Rows older than the window's start are counted (`rows_before_window` in diagnostics, one INFO line per coordinator) and left out, and a page that reaches below its window ends it. A past row at or after the window's end fails the sync (`invalid_data`): Meridian read the window a day late, say. A row still to come, such as an estimate for the rest of today, which Meridian's `COMBINED` quality may return, is no reading: it is left out of the rows, and of what a window returned for the stop rules and the refusal checks, so a window holding nothing else is empty. It still counts for the page guards, and for the edge hours of the debug line. A per-hour map of channels replaces the scan of every kept row, and the checks that an hour's readings can be told apart apply within one window.
- **Dates read shifted** fail closed too (`_Walk.check`, on each complete window). Each window keeps the hours and channels of its rows from before its start, and the next older window must have returned every one of them: so it does when Meridian ignores the start, and it does not when Meridian reads the dates a day early, which would leave each window's last date out of every window. A window with readings but none on its last date, after a newer window that returned its first hour, is what an excluded `endOn` gives, in every window: once, or in windows apart, it is taken for a gap a meter may have (which dates are windows' last depends on the day the walk runs); in two windows in a row it fails the sync. A bound read as exclusive at the hour, the first hour of `startOn` or the last of `endOn` left out, takes from every window an hour no other window returns, and its row count does not show it: at each boundary between two windows with readings, one window returns its edge hour and the other does not. Once, or at boundaries apart, that is taken for a one-hour gap; at two boundaries in a row it fails the sync. An outage across a boundary leaves out the hours on both sides and fails nothing. These two checks apply to windows next to each other, so they stay off with the one-day overlap switched on (below), whose older window returns the newer one's first date, edge hours included. Dates read an hour early or late fail one of these checks, or the one on rows after the window, too. How Meridian maps dates to hours is still to be confirmed against the live service.
- **Guards.** An empty page ends a window, unless it says more pages exist, which is an error; so is a page that reaches no older readings than the previous page (a page boundary can fall inside an hour on a meter with several channels, so a page that ends at the previous page's oldest hour with readings no earlier page held moves the window on), a start cursor that did not change, and more pages in one window than 11,904 rows need at its page size: a 17th page of 744 rows, a 57th of 214.
- **Stop rules.** A walk goes on past an empty window with nothing stored in it, and two empty windows in a row after a reading mark the start of the history. Empty windows with hours stored older than them mark nothing, as after a long downtime in which the meter sent nothing for some weeks after the newest hours stored: the walk goes on to the stored hours (`_take_window`). Empty windows before any reading mark nothing either: a supply that ended weeks ago, still listed because the topology asks for every property active since 1970, or a meter that sent nothing for a while, has empty newest windows and readings before them, so the walk goes on to the cutoff, as one request for the whole span would. That holds in every initial import, not only setup's. Setup hands the entry the directions whose initial import searched every window it planned, or imported readings (`SyncMemory.searched`), and the entry's first sync gives a direction without statistics that setup searched the mode the cadence asks for, the hourly update (`_searched_by_setup`); readings that come later queue its initial import (`_pending_backfill`). Nothing else records which directions were searched, so after a restart or a reload a direction with no statistics may be one setup found nothing for, or one no setup searched, such as an account added through Reconfigure (which only updates the selection and reloads), an account added on its own, or a property that appeared later. A direction with no readings in 90 days so sends 13 requests at setup, 1 in the entry's first sync, and 13 again in the first sync after each restart or reload; setup and each restart or reload log one INFO line that it found nothing. A window with no readings where Home Assistant has stored hours stops the walk.
- **Refused windows.** Meridian's web app never asks for dates before the supply started, and clamps `startOn` to the supply start, so Kraken may refuse such dates instead of returning nothing: perhaps only a window that ends before the supply, perhaps any window that starts before it, the week holding the supply start included. Only a window older than every reading returned so far, refused before it returned any reading of its own, may be such a refusal (`_is_refusal`): with a GraphQL error that has a code other than a query over Kraken's limits or a missing account or property (so a missing property still refreshes the topology and tries again), or with a client error (HTTP 4xx) from Meridian's service (`MeridianRejectedError`), never one from Google's session service, and never a GraphQL error without a code (`UNKNOWN`, as for a failure inside the service). Then (`_async_fetch_or_refused`):
  - a refused window of one day is not asked for again, since it would be the same request and a GraphQL error is never resent. After a newer reading, as a date of a walk asked for by day or one a lane's coverage asks for alone, the date before it is asked for, as for a longer window's dates (below): only its refusal, or no readings for it, makes the refused date the start, and readings for it fail the request (`_async_confirm_refused_day`). The walk's oldest date, or the lane's target date, is the start without that, which leaves out that one date at most;
  - a longer one is asked for by its dates alone, newest first (`_async_fetch_refused_days`), whether or not the newer window's readings reached its first hour: readings that stop short of it may start inside it, or have a gap at 00:00 on its first date, so they do not show where the history starts. Its newest date refused, or with no readings, after a newer reading, makes the window the start; a supply that started inside the newer window so costs one request more.
  - refused before any reading, a window of one day, or the newest date of a longer one asked for alone, is taken for a property whose supply has not started yet, such as a new address added to an account before a move, when the refusal is a GraphQL error with a code and the direction has no statistics at all (`_Walk.may_precede_supply`): there is no history yet, nothing is imported, and one INFO line gives the code, so the account's other properties still sync. A client error there fails the sync, since it is what a request Meridian cannot take at all gets, for every property. So does any such refusal for a direction with statistics, inside the sync's span or older, as in an hourly update while Meridian publishes readings more than a day late: its statistics show there is a history (`_async_fetch_since`'s `has_statistics`, from the statistics cached for the mode, not the span's stored hours). A refusal of another kind taken this way loses nothing: the direction still has no statistics, so the next coordinator imports it as new, and readings returned in an hourly update queue its initial import. Dates that come back join the window's rows. A date refused after a newer one came back may be the day before the supply started, and the date before it is asked for too, past the window's first date if need be: only its refusal, or no readings for it, confirms that the history starts after the refused date, and the newer dates are kept; readings for it fail the sync, for the setup retry or the next update to fetch the window again rather than keep the newer dates alone for good. A refused date that is the walk's oldest needs no confirmation. When every date comes back, the refusal was of another kind: the window's rows are those of its dates, and the walk goes on. That is 8 more requests at most, each date one more window requested in diagnostics; an empty date older than every reading logs no page line.
  - the start must leave no stored hour before it, or the refusal fails the sync. Stored hours from the start on do not count against it: the restart and weekly reconciliations, whose 14 days can still reach before a recent supply start, or before a feed-in register's, meet the refusal setup met, and take it the same way.

  A window refused after its first page returned readings fails the sync. How Kraken answers for dates before a supply starts, with no readings or with which error, and for a property whose supply has not started at all, is still to be confirmed against the live service.
- **The one-day overlap** (`WINDOW_OVERLAP_DAYS`) is held in reserve at 0. Set to 1, each older window ends on the day the newer one starts, and an hour both return counts once when its readings are identical; different readings fail. It is meant for a live check that finds Meridian's window edges shifted, or an edge hour left out, which the older window then returns.

### Stored-aware imports

The replay (Statistics, below) keeps the running sums consistent on its own: it writes again the stored state of every stored hour in its span that it was not given, and shifts the rows after its span. These rules decide what an update imports when Meridian stops returning readings Home Assistant has stored, which stay as stored. A direction whose energy statistic has stored rows reads the hours its energy and cost statistics have stored, once a sync (`statistics.async_stored_hours`, one executor read), and:

1. stops its walk at an empty window over stored hours (above);
2. leaves out every row up to the newest stored hour inside the fetched span that Meridian did not return (`windows.importable`); a hole with nothing stored in it leaves nothing out, so both sides of a gap are imported;
3. imports nothing that sync, with one INFO line, when stored hours are newer than every row left;
4. writes the cost only of the hours after the newest hour to import that has no cost where a cost is stored (`cost_after`), from that hour's stored cost sum, with one INFO line (`windows.cost_plan`): the usage is written for every hour, and the stored cost rows up to that hour keep theirs. So the cost is cut where the usage would be cut at a hole, and the hours after it, the new ones included, get their cost in the same import, however far back it reaches. Should stored costs still be newer than every hour left to import with a cost, no cost is written (`import_cost=False`), with another INFO line. Hours with no cost at all, as when Meridian publishes an hour's usage before its cost, write no cost row, so nothing waits for them.

Rows left out are left out of the measurement cache too, so a later sync compares them again. The merge works on a copy of the cache, which replaces it only once the replay has confirmed its writes: a replay that raises, `statistics_write` included, leaves its rows to be offered again by the next sync, from the same hour, instead of taking them for rows already written, and its replay heals what the recorder saved in part. The rows fetched for an hour replace that hour's cached rows, those of channels the fetch no longer returned included (`_merge_hours`): a window joins the direction's rows only once every page of it has come back, so the latest fetch of an hour holds all of it, and the hour is never counted from the channels of two fetches. Until 0.3.0 a change in an hour's channels, as when a meter's registers change, failed every sync with `invalid_data` until the cached rows aged out. A cached ACTUAL row is still kept over an estimate of it. The weekly reconciliation's rows are replayed from the oldest hour it fetched, changed or not (`whole_window`), so a seam its replay meets inside the last 14 days is rewritten once a week. The rows of an import whose cost was not written are cached without their cost (`_uncache_costs`), so the next sync that fetches them finds their cost changed and writes it as soon as no hour in its span blocks it. Diagnostics report `stopped_at_gap` when the walk stopped or was cut at a gap over stored rows.

### Units, isolation and the size ladder

A unit is one direction of one property (`(property key, direction)`). Every sync plans all units first: each one's mode, cutoff, stored hours and windows (`_async_plan_unit`). Then every unit's newest window is fetched before any unit's older ones, so each unit's first request starts early and the start reserve can only hold back older windows; then each unit walks on, and is imported (`_async_finish_unit`) (`_async_run_units`). The newest windows go in topology order, except that units the last syncs' time budget did not reach go first (`UnitState.not_reached`), so a slow Meridian does not leave the same units out at every update. A unit whose property is cooling down after a gateway timeout waits behind the units that can send at once, in both passes: one property's cooldown never holds up another's requests. In the second pass, units that can send at once go first, then those whose cooldown ends soonest; among them, the units of a property whose walks have returned readings in this sync, then a unit whose newest window is not yet fetched in full (one skipped for its property's cooldown, or whose newest week is asked for by day), one that has fetched none of it before one part-way, then units whose walk has returned readings, then topology order (`_next_walk`). After each window a walk lets a unit that comes before it go first, and resumes after (`_comes_first`): one that comes to wait for its property's cooldown, in setup before a probe, lets a unit that can send go on, and one on its older windows lets a newest window go once its cooldown has passed. So when one direction's newest week times out in setup, the property's other direction, which waited with it, sends its newest week right after the probe, before the rest of that week's days and before the property's older weeks, and setup can still keep both directions' newest weeks when the time limit then runs out, rather than the first direction walking all its weeks before the other sends anything. Once every unit's walk is done, each unit whose walk went through asks for a few windows more of its older history (see Lanes). Properties with recent data still go first, and an ended property's newest weeks and probes wait behind the active property's weeks.

- **Isolation.** A failure stops its unit's walk alone (`_async_walk_unit`), and is recorded as its error. A rejected session and a rate limit stop the whole sync, and so does a missing account or property while the topology was not refreshed in the sync, which refreshes it and syncs again, as before. The end of the time budget stops every walk that still has a window to fetch. Polling succeeds and publishes when at least one unit imported, in full or degraded (below); otherwise the first unit's failure fails the sync, a refused replay (`statistics_refused`) only when no unit failed otherwise, since no retry clears it, or, when every unit waited out a backoff, the last failure of the first, as `UpdateFailed` with its key and detail. A recorder error while importing still fails the sync.
- **Import rules.** A walk that ended without a failure is imported as before. One that stopped early (a failure, the size ladder or the time budget) imports the windows it fetched and kept (`walk.completed_on` set; a window whose rows failed their checks was dropped, and does not count), with statistics or without, and whether or not they reach the frontier: newest first, they are one block back from today, and the replay writes them behind any newer stored rows, or with older ones before them, consistently (see Statistics). Until 0.3.0 one failed request failed the whole sync and discarded every page it had fetched, so a slow Meridian could leave a first import unimported at every update. The days between the stored history and the new rows are filled in later: the reconciliation the unit then owes covers the last 14 days, and its lane's coverage the older ones, whose failed window's dates wait 1 h, then longer, before they are asked for one at a time (`_note_lane_failure`, `lanes.LaneState.fail`). That is the walk's window it failed at (`_Walk.failing`), not its last request, which may be one of its dates asked for alone, or the date before a refused one, which came back. The unit is then degraded. An initial import that imported readings this way counts as done (`_record_direction_fetch`): its lane's coverage asks for the rest, rather than its 90 days being walked again. A walk that fetched no window imports nothing.
- **Backoff** (`units.UnitState`, in memory only). A failed unit waits 1 h, then 2 h, doubling up to 24 h, before it is fetched again (`deferred`); a degraded one runs the hourly update meanwhile, and its owed reconciliation (`full_reconciliation` after a restart, weekly or initial sync, the daily one after a daily) waits the same way, then runs, or a larger mode if the sync asks for one. An hourly update while it waits leaves the unit degraded, owing that reconciliation, with its wait unchanged: only a sync that covers what it owes (`UnitState.covers`) clears it. An initial import that stopped early but imported readings counts as done, and its lane's coverage completes it (import rules, above); only one that stopped before any reading leaves the backfill pending (`_record_direction_fetch`): it waits the same way, then walks the 90 days again. A degraded unit whose owed reconciliation imports nothing, as when its newest window times out, stays degraded: the reconciliation waits longer (`UnitState.defer_reconciliation`), and the hourly update, which has kept working, goes on meanwhile, rather than the whole unit waiting. Its one INFO line names Meridian only when Meridian's history did not come back: one whose replay Home Assistant did not confirm (`statistics_write`), or that was refused (`statistics_refused`), says so instead (`_RECONCILIATION_UNSAVED`). When that hourly update fails, the unit fails and waits 1 h, then 2 h, doubling up to 24 h, counting its failed hourly updates in a row alone (`UnitState.fail_hourly`, `hourly_retry_at`); the reconciliation keeps its own count and wait, and once an hourly update imports again the unit is degraded again (`recover_hourly`). Counted with the reconciliation's failures, one timed-out hourly update waited as long as the reconciliation, up to a day, and with one direction every update failed until then. A unit due a minute early is not held back, since Home Assistant schedules an update an hour after the last ended. Before the first sync has succeeded, every unit is tried at each attempt: the first sync's own retries are spaced out instead, and no attempt counts towards a unit's wait, so a unit still failing when a first sync succeeds waits 1 h. The global cadence is recorded after every successful sync; the owed reconciliation is per unit, so a unit that skips the reconciliation a sync runs, because it waits out a backoff, its reconciliation waits, or the time budget ran out before its first request, owes it (`UnitState.owe`) and runs it when it is next tried. A unit the budget did not reach did not fail: it logs no warning, one INFO line the first time for the coordinator, and goes first at the next sync. A unit that starts failing logs one WARNING, with its direction, account and property positions, reason and HTTP status: in an hourly update at once, so a rate limit or a refresh of the accounts that ends or restarts the update later cannot lose it; in setup once the import is known to go on (a failed setup attempt logs its own warning), a unit that failed before a refresh of the accounts included (`_report_failing`). It says when it is tried again: in about so many hours; during a first sync after a restart or a reload, by the next update; or, from a setup import that succeeded, by the first update after setup, which logs no second warning for it (`SyncMemory`); a failed or degraded unit that imports in full again logs one INFO line, and so does a failed one that imports its newer windows, degraded, or whose hourly update imports again while its reconciliation waits (`_note_recovered`); one that failed in setup before a refresh of the accounts, which never warned, logs neither.
- **The size ladder** (`_async_walk_step`, `_ladder`). After a gateway timeout (HTTP 504 or 524, or no answer) of a window longer than a day, the setup import waits out the property's cooldown and asks for the window's newest day alone, the probe (`probe_1d` in the failed page's debug line). The probe answered, the window's other days follow one at a time, and the walk goes back to weeks; a second week that needs the ladder keeps days for the rest of the walk (INFO). A probe that times out too shows that size is not the lever, and the walk stops (INFO): 2 requests and about 195 s. A day that times out after the day after it came back is a bad day: the walk stops, and the import rules apply. Polling stops at a unit's first gateway timeout, so a unit has at most one per poll: the window's newest date is remembered (`UnitState.probe_on`), with its length (`probe_days`), and the unit's next walk fetches the first window holding that date that is as long by its days, starting with the probe, then goes back to weeks. The probe is forgotten once it has gone out: one the time budget stopped before it went out, as an older week's probe late in a slow update, is still owed, rather than the next walk asking for that week whole again, to time out again. A shorter window holding it, as the hourly update's two days while a degraded unit's reconciliation waits, is asked for whole and leaves the probe to the next window as long: it shows nothing about a week's size. A probe that came back is remembered for a week from the update that learned it (`UnitState.laddered_on`, `laddered_at`), whichever window it was: counted from the window's own date, a probe of any window but the newest, which ends a week or more before today, was forgotten in the update that met it, and a walk whose newest week answered and whose older weeks timed out alternated for good between asking for the second week whole and by day. A window that then times out, an older one in the same walk or the same window asked for whole again at a later update, as the hourly update's own window, is the second that needs the ladder: later updates ask for every window starting on or before the newer of the two dates by day (`UnitState.days_on`, `_defer_ladder`, INFO once), as setup keeps days after a second laddered week. A newer window, once the newest starts after that date, is asked for whole, and the unit forgets each date a week after the update that learned it (`days_at`; `days_kept`, `recent_ladder`), so a Meridian that has recovered is asked for weeks again. A probe is planned only when no probe that came back is remembered, and only that probe can come back, so a probe that times out meets none. Without this, an update would ask for the first week whole again, which timed out again, and a walk would never get past it, nor a single-window walk stop failing every other hour. A query Kraken refuses as over its complexity or node limit (`KT-CT-1188`, `KT-CT-1189`) is split into days once (`split_1d`), for the rest of the walk: the refused week, then up to 91 dates one at a time, 92 requests for 90 days instead of 13; a second occurrence stops it. A failed window's rows are dropped with it, so its days never meet them, and a day counts as its share of its window both for the progress and for the two empty windows that mark the start of the history: it takes two weeks of empty days, not two days.

### Resends, pacing and the time budget

- **One resend, at most.** The resend wraps the client's call, whose own loop renews a rejected session once: so a resend never forces a session refresh, and a resend that is rejected still gets its own refresh. A passing failure (HTTP 408, 502, 503 or 520-523, or a network error) is sent once more after a random 2-5 s. After a gateway timeout (HTTP 504 or 524, or no answer within the 75 s limit), a resend's included, no request goes to the property for 75 s, or as long as the failed request took: the service behind the gateway may still be working on it. It is never resent as it was: the setup import's next request is the size ladder's probe, after the cooldown, and polling leaves it to the next poll. The probe is a new call to the client, so it too reuses a valid session and renews a rejected one once. Rate limits, GraphQL errors, client errors, other server errors and data that cannot be used are never resent. Only measurements requests are resent: an account request that fails still ends the sync, and a billing request that fails still keeps the cached billing details, as before; a later attempt or poll is their retry.
- **Kraken's in-band errors.** `KT-CT-1199`, Kraken's rate limit, arrives in an HTTP 200 body and is raised as a rate limit of an hour, which stops the sync; polling then waits that hour, doubled for each rate limit in a row, up to a day (`_rate_limit_wait`). `KT-CT-1188` and `KT-CT-1189`, a query over its complexity or node limit, split the walk into days once (above); a second occurrence stays `invalid_data` and names its code. Neither is ever resent as it was.
- **Pacing.** Measurements requests start at least 1 s apart, so no sync sends more than 60 a minute.
- **The time budget.** The setup import has 240 s (`SETUP_IMPORT_BUDGET_SECONDS`) within its attempt's 300 s limit, and each hourly update has 240 s too (`POLL_BUDGET_SECONDS`): no measurements request after the first starts once less than 80 s of it remain, enough for one to time out (`RunBudgetError`). An update that walks a direction back further than 14 days, an initial import or a catch-up after a long outage, has 900 s instead (`DEEP_WALK_BUDGET_SECONDS`, `_extend_budget`): it imports what it fetched either way, but a search for a supply that ended must finish to leave the unit quiet, or it would walk back again at every update. That covers a property setup left out, accounts added later, and the first sync after a long outage. A quiet unit's walk counts only once its newest window has readings again and its cutoff is more than 14 days back: the budget is then extended before its next request (`_async_walk_step`). Its newest windows still go first. It stops the walk it came in, and every later walk at its next request; the import rules then apply to each. In setup, when no property imported its newest windows, the attempt fails with `import_timeout` (`SetupTimeLimitError`, raised by the flow from it), its form saying that too little of the import's 4 minutes was left for another request; when a gateway timeout and its cooldown cost that time, it fails with `upstream_timeout` instead, and the form offers to continue without history (see Setup). In polling, an update that imported nothing fails with `upstream_timeout` and the detail "the update's time limit ran out". A resend or probe needs that reserve after its wait too: 80 s after a passing failure's pause, 155 s before a gateway timeout's probe. The time each unit's import takes is not counted (`_async_uncounted`), in a deep walk's 900 s too, as when a quiet unit's walk extends the budget only after other units have imported: its replay waits for the recorder to save and confirm its rows, up to 90 s behind a busy recorder (a backup, say), and up to 60 s before that when the last replay of its statistics was not confirmed; counted, that would leave the windows other units still have to fetch too little of the budget, and fail them with `time_budget` as if Meridian had been slow. The setup attempt's 300 s limit, the `asyncio.timeout` that bounds it, moves on by the same time; while an import runs, it leaves it at least 180 s (`REPLAY_ALLOWANCE_SECONDS`: the replay's three barriers, the two it may wait behind before it reads, and 30 s for its reads), so it does not cut short a replay that started near its end.
- **Progress.** The setup dialog's progress (`async_update_progress`) is the fraction of the planned windows done; a refused window whose dates are asked for alone counts once, and a walk that stops early counts the windows it no longer needs as done, the window Meridian refused at the start of the history included.

### Lanes: completing the history

A lane is a unit seen as a history to complete (`lanes.py`). Its target is New Zealand midnight at the start of the older of the date 90 days back (`backfill_start`) and the first date of the account's current billing period, never more than 400 days back, then the first midnight after that (`coverage_target`): the bill totals need every hour from the period's start. A midnight, so every date the lane asks for is asked for whole, and a date fetched in full never lacks hours that a target moved back later needs, as once the billing period is known; an initial import keeps its rows from 90 days back to the hour, so the update after it asks once for the hours of that date before them. Nor is the target newer than a date whose import was not confirmed (`unsaved`, below): such a date is replayed in full however the billing period moves, until a replay writes it again. The billing period is the one an earlier update cached. A coordinator's first sync, after setup, a restart or a reload, asks for no coverage (`_covers`), so the lanes plan with the period it fetched; when that request failed, they reach back 90 days until an update knows the period. Nothing is kept in a Store: each sync reads the lane's stored energy and cost hours once, from its target on (`_async_plan_unit`), which its walk goes by from its cutoff on, and the lane's own state in memory (`LaneState`) holds only what the recorder cannot tell, so a restart starts from what is stored, and so does a reload, but for the dates whose import was not confirmed:

- the dates fetched in full (`fetched`), whose missing hours Meridian does not have, and of those the ones with no readings (`empty`), from coverage windows and from walks, for dates older than the newest stored reading's (a newer date may still be published) and whose midnight the walk's cutoff reached (`_note_lane_walk`, `_walk_days`); never a date holding stored hours that came back with no reading, nor any date of the empty window over stored hours that ended a walk: nothing shows Meridian read them in full;
- the newest date of a window Meridian refused as before the supply started (`refused_through`);
- the dates whose request or import failed, each with the time it is tried again, 1 h, then 2 h, doubling up to 24 h for that date's own failures in a row (`bad`, `tries`, `fail`), so a date that keeps failing waits longer while others come back, and of those the dates whose import Home Assistant did not confirm (`unsaved`), which an entry also keeps across its reloads, each with the time it is tried again, in `hass.data` (`UNSAVED_COVERAGE`), handed over at the end of every sync, however it ended (`_keep_unsaved`), and a new coordinator's lane takes over (`restore_unsaved`): the recorder may have saved their rows without the shift of the rows after them, which no stored state shows. Such a date is confirmed only by a confirmed replay that wrote every hour of it stored for usage, and for cost, again (`_replayed_days`), its window's or a deep walk's: one that came back with no readings, or without its first stored hours, or that a walk's replay started after, stays unconfirmed and waits again. An update cancelled during a window's import, as by an unload of its entry, leaves the window's dates unconfirmed too. A restart of Home Assistant forgets them, as it forgets an unconfirmed deep replay's oldest hour;
- the monthly revision pass (`revision_on`, `revising`, `revised`), and what it forgot to ask again, until it has asked (`known_fetched`, `known_empty`, `known_refused_through`), for what the lane reports alone.

The setup import hands its lanes to the entry with the rest of its memory (`SyncMemory.lanes`).

**Order in each update.** After every unit's newest windows (1) and the rest of its walk, the reconciliation or catch-up of its mode (2), each unit whose walk went through in this update and that has stored hours to go by asks for at most 6 windows more (`COVERAGE_WINDOWS`), coverage (3) (`_async_cover_lanes`), but in a coordinator's first sync, whose result the entities wait for and which has no billing period yet (`_covers`): first the dates still missing, newest first (`missing_days`), then, during its revision pass, the stored dates not yet asked for again (`revision_days`). The setup import does not; a lane without statistics has its initial import instead, whose 13 windows are its first run's coverage. Nor does a unit whose walk was its initial import, which walked 90 days in this update, nor one whose initial import is queued for the next update, as for readings that first came in an hourly update (`_covers`, `_pending_backfill`): that import would walk again the weeks its coverage had just asked for. Its coverage starts at the update after. The units take turns, a window each, so each gets some of the time budget, and each request starts 2 to 5 s, at random, after the last one ended, so a slow Meridian gets its pause too (`COVERAGE_PAUSE_SECONDS`, `_async_before_request`, `_last_measurements_end`). Dates in a row join one window of a week at most; a date tried again after a failure goes alone (`plan_spans`), as asking for less may then help. Each window is planned again after the last, so one that marks the start of the history ends the lane's coverage there.

**Which dates are missing.** A date from the target's on with an hour, from the target and up to the frontier, that is not stored; not one fetched in full already, nor one waiting after a failure; and one whose wait has passed, even with its usage stored, since an import Home Assistant did not confirm may have saved its usage without its cost. A date whose fetched rows the stored-aware rules left out, by a walk's import or a window's (`importable`, `ImportPlan.newest_hole`), is not taken as fetched (`_Unit.left_out_through`): the update's coverage asks for it if it misses an hour, and a window's date that still misses one, or that waited after a failure, waits again (`fail`), so a hole Meridian no longer returns is not asked across at every update. Only the hours older than 14 days back are asked for, the date 14 days back included for its hours before the reconciliations' cutoff, and none of a date the update's walk fetched in full, nor after the frontier's date (`coverage_end`): the reconciliations revise the last 14 days, and an hour missing between their stored hours widens the daily reconciliation instead (`missing_recent`, `_mode_since`), from 48 h back to 6 h before it, at most 14 days. A gap that started before the 14 days, after the newest stored hour older than them, counts from their first whole hour, so the daily reconciliation reaches back 14 days while the gap ends inside them; the coverage asks for its hours before that. Hours before the oldest stored hour are not between stored hours, so a short history widens nothing. The hours after the frontier are the walks' to fetch, or have no readings, as after a supply ended.

**History start.** A refusal of a window older than every stored hour, as a walk's, marks the start (`_async_fetch_or_refused`, `refused_through`), unless stored dates at or before it show the history goes on. Otherwise 14 dates in a row before the oldest stored date that returned nothing mark it (`LaneState.history_start`, `EMPTY_DAYS_AT_HISTORY_START`): two empty weeks, as the walks count them, and robust across meter-communication gaps, since empty dates between stored dates, or a gap shorter than two weeks, start nothing. The run of empty dates is kept across updates, so a stop found over two updates still holds; after a restart it is found again, with two or three windows. A coverage window counts the oldest stored date as seen in full (`_Walk.oldest_seen`, its next midnight): a history may start on that date after midnight, and Meridian may refuse any window that starts before the supply did, so a window ending on that date that is refused before any reading is asked for by its dates (`_async_fetch_refused_days`), whose refusal of the date before the first marks the start. A date asked for alone, as one tried again after a failure, that is refused after newer readings is confirmed the same way: the date before it is asked for too, and only a refusal of that date as well, or no readings for it, marks the start (`_async_confirm_refused_day`). Readings there show the refusal was of another kind: the date fails, waits and is asked for again, rather than the history being cut off at it for good. A date at the target needs no confirmation, as it leaves out that one date at most. Once the start is known, the dates before it no longer wait after a failure (`forget_bad_before`), as none of them is asked for.

**Window edges.** A walk checks its windows against the newer ones for an `endOn` read as excluded or dates read a day early (`_Walk.check`), as how Meridian reads a window's edges is still to be confirmed against the live service. A coverage window has no newer window of its own, but the stored history after it shows what its end should hold (`_async_check_cover_edge`). When its last hour came back with no reading although the hour after it is stored, or its last date with none at all although the history goes on after it, up to the frontier, and the date after is not known to have none (`empty`), Meridian is asked for that date and the next together. Readings for the last date that the window did not return show it was misread: the window fails, so none of its dates counts as fetched or as empty, and they wait, then are asked for again, a day at a time, each failing the same way while the misreading lasts, so the lane never reaches its target with a date left out. None confirm a gap, as a meter that sent nothing then, and the window is imported; so does a refusal of that request (`_is_refusal`), as Meridian may refuse one that starts before the supply did, which shows nothing of how it read the window. An empty window that ends right before a stored hour, as before a history that starts at midnight, costs that one request more; the next older empty one does not, as the date after it is known to be empty.

A window's start is checked the same way (`_async_check_cover_start`), as the walks check each boundary from both sides and a coverage window has no older window of its own. When its first hour came back with no reading, though its rows reach it from the target on, or its first date with none at all, while the window returned readings on another date or holds that date alone, and the history may go on before it, Meridian is asked for the date before and that date together. The history may go on before it when the hour before it is stored, or when the date before is neither before the history's start, once known, nor known to have no readings (`empty`): so a window that starts on the target's date is checked too, whose first hour a billing period's totals need. Readings for the first date that the window did not return show that Meridian read its `startOn`, or that date's first hour, as excluded: the window fails as above, and so does each of its dates asked for alone, an empty one included, rather than count as empty towards the history's start. None confirm a gap, or where the history starts, as a supply that started during that date, and the window is imported; so does a refusal of that request. An empty window of more than a day is not checked: reading its first date or hour as excluded would leave its other dates' readings, and it is what the weeks before a history's start return, so those weeks cost no request more. The oldest window of a walk is not checked this way either: a walk has no stored history before its cutoff to go by, which is what a coverage window asks for.

**Imports.** Each window is imported once fetched (`_async_import_coverage`), within the window: the stored-aware rules apply to its own stored hours (`importable`, `cost_plan`, the latter judged by every row returned), and only the hours whose usage or cost is not stored as fetched are given to the replay (`statistics.changed_hours`, against `async_stored_states`), which writes from the first of them to the last, behind the newer stored rows, and shifts those to follow on. A window that changed nothing writes nothing. A window holding a date whose import was not confirmed (`unsaved`) is replayed in full instead (`whole`): the recorder may have saved its rows but lost the shift of the rows after them, which no stored state shows, and a replay of the same hours writes both joins again. Such dates fail nothing: they wait 1 h, then go again, a day at a time, also after a reload (above), until a replay writes every stored hour of theirs again. A window's dates holding stored hours that came back with no reading count as left out, as a walk's empty window over stored hours ends the walk: one with an hour missing, or that waited after a failure, waits again, and none counts as empty. A failure (any but a rejected session, which still fails the update) fails nothing else: the window's dates wait, the lane's coverage stops for this update, and after a gateway timeout so does its property's; a rate limit and the end of the time budget stop every lane's. A rate limit is waited out all the same: no lane's coverage runs until Meridian's wait has passed, doubled for each rate limit in a row (`_rate_limit_wait`, `_coverage_not_before`), and the update, which succeeded with its own data, makes the next one wait as long, never less than the hourly interval, by setting the coordinator's `update_interval` for that one interval (`_honour_coverage_rate_limit`): an update asks Meridian for its walks as well. Nor does that update ask for the billing period once its coverage met the rate limit (`_async_billing_period`): it keeps the cached period, and withholds one that has ended, as when that request fails, since a second rate limit there would fail the update and make every entity unavailable. A lane reaches its target when no date from its target on misses an hour Meridian may still have, and none waits after a failure with an hour missing or after an import not confirmed (`lanes.reaches_target`): a revision pass still running leaves that as it was, as what it forgot to ask again counts until it has asked (`known_fetched`, `history_start(known=True)`), whether that request is still to come or keeps failing, and a stored date whose revision keeps failing has nothing missing. A lane whose walk went through with nothing stored from its target on, as a grid export that never exported or a supply that ended before the target, reaches its target too: it has nothing to complete (`_lanes_to_cover`). A lane's history start is found once known (`history_start_found`), which a revision pass asking again does not change either; diagnostics show both as booleans, never a number of days, which would tell how long the history is, and both as no after a coordinator's first sync, which asks for no coverage, until the update after it has looked, but for a lane with nothing to complete.

**The monthly revision.** Estimates older than 14 days were never corrected: the merge compares fetched rows only with the 14-day cache. On one day of the month, 1 to 28, spread by a hash of the lane's key (`revision_day`), so the grid import's and export's days may differ or match, or at the first update that covers the lane in the 3 days after it (`revision_due`, `REVISION_GRACE`), a lane starts a revision pass (`LaneState.start_revision`): its updates ask again for every stored date from the target to 14 days back, 6 windows at each with its coverage first, and the import compares them with the stored states instead of the cache, so only hours Meridian has changed since, or did not have before, are written again. The pass also forgets the dates fetched and empty, and the refusal that marked the start (`refused_through`), so it asks again for days Meridian may have published since, and finds the history start again, whether empty weeks or a refusal showed it. What it forgot is kept apart until it has asked again (`known_*`), so `reaches_target` and `history_start_found` do not change while it runs; what it finds, as older readings Meridian has published since, counts instead. A stored date whose revision fails is left out of the pass (`revision_days`): it waits, then the coverage asks for it alone, and the pass goes on past it. It costs about 11 requests a month for a lane with 90 days. What remains: a revision made after a pass waits for the next one; one of an hour older than the target is never corrected; a manual Adjust sum on any hour from the first to the last hour a window writes again, or on the hour after them, is undone (`async_replay` rebuilds that span and resets the row after it), as it is for the windows that fill in missing days; a pass missed for more than 3 days after its day waits for the next month; and, as the pass is in memory only, a restart before a pass ends leaves the rest of it to the next month, while one on the lane's day or in the 3 days after starts it again.

**Load.** A complete lane adds no request to any mode: the initial import still sends 13, the hourly update 1, the daily reconciliation 1 to 3, the weekly one and a restart 3 (`test_each_mode_sends_as_many_requests_as_before_once_complete`), and no update sends an initial import's 13 and coverage as well (`test_an_initial_import_leaves_the_older_days_to_the_next_update`). The update after an initial import, or a catch-up walk cut at 90 days, asks once for the hours of the target's date before that cutoff, as the target is that date's midnight: one window. Filling 76 missing days takes 11 windows over two updates. A window whose last date or last hour came back with no reading, while the history goes on after it, costs one request more, for that date with the next, and one whose first date or first hour did, while the history may go on before it, one more, for the date before with that one (window edges, above): the window that holds the start of a supply that started during a day costs that one request after each restart or reload. A history shorter than its target costs two or three windows at the update after each restart's or reload's first sync, to find its start again, with one request more for the first date of the window holding the start, as above, while its empty weeks cost none (`test_a_short_history_costs_no_backfill_but_once_after_a_restart` counts both), and nothing after that. Its INFO lines then say that the history may only be finding where it starts, and that it is complete back to there.

## Statistics

Each property gets external statistics `meridian_energy:<kind>_<key>`, where `<kind>` is `consumption`, `consumption_cost`, `generation` or `generation_credit`, and `<key>` is the first 12 hex digits of a SHA-256 hash of the account number and property ID. IDs therefore carry no identifiers. Generation statistics exist only for feed-in meters.

Every import goes through one primitive, `statistics.async_replay`: the setup flow's and every entry's. For each statistic it writes one span, from the first hour it is given to the last:

1. **The predecessor, by time.** The running sums follow on from the newest stored row with a sum before the span, looked for in the 14 days before it, then back to 800 days before it, with hourly periods only: a month period returns a newer row's sum when no predecessor exists. Rows without a sum, which another writer such as Home Assistant's statistics import can store, are passed over, as `async_latest_numeric_statistic_start` passes them over for the coordinator's frontier, so the two agree on whether a statistic has a running total to continue. With none, the sums start from zero, unless rows are stored before the span all the same, older ones or rows without a sum: the replay then refuses (`StatisticsAnchorError`, a `StatisticsWriteError`) and logs one WARNING for the statistic, rather than put the new rows below them, and writes nothing. Its unit fails with `statistics_refused`, not `statistics_write`: a retry refuses again until those statistics change, so a first sync that fails so waits for the hourly update rather than its short retries (one in which another unit failed otherwise fails with that unit's failure, and keeps them: Isolation, above), and the setup form says what is wrong instead of advising a wait. Until 0.3.0 the lookup read the newest 2,232 rows (the 90 days of an initial import and 72 hours more): enough while no import reached back further than 90 days, as none did then, but a replay behind more rows than that would have started from zero again.
2. **Stored states fill the span.** Every stored hour in the span that the replay was not given is written again with its stored state, so its sum follows on from the new rows. An hour whose cost is None is not given for the cost, so its stored cost, if any, is kept.
3. **The rows after the span are shifted.** Every stored row after the span is shifted by one constant with the recorder's own adjust task (`get_instance(hass).async_adjust_statistics(statistic_id, last + 1 h, delta, unit)`, where delta = the last row's new sum + the next row's state − the next row's old sum): one update per statistic instead of writing every later row again. The first row after the span then steps from the last row written by its own state, so an "Adjust sum" a user made at that hour (**Settings → Tools → Statistics**) is undone, and a seam there healed, even when the replay writes the values already stored; one made at any later hour is kept, since every row after the first keeps its step. One made inside a replayed span is overwritten: in the 14 days that every restart or reload replays, as before, and, since 0.3.0, those of the weekly reconciliation, which until then wrote only from the first hour that changed. While every walk reaches the newest stored hour, the span ends there and nothing is shifted; the shift is what lets a backfill write older history behind newer rows.
4. **Queued together, under a lock.** A replay holds one lock per statistic (`hass.data[DOMAIN]["write_locks"]`, shared by the setup flow and every entry, taken in one order) from its first read until its writes are confirmed, so two writers of one statistic take turns. A replay that is not confirmed releases its locks with its writes perhaps still queued, so it leaves its statistics marked (`hass.data[DOMAIN]["replay_unsettled"]`, set before it queues its writes, cleared once they are confirmed or waited for), and the next replay of them first waits behind two barriers (`SETTLE_BARRIERS`, the second behind an import the recorder queued again) before its first read: it never continues running sums the recorder has yet to save, which would leave a seam where the two meet once both are saved. When one of those barriers times out, it raises `StatisticsWriteError` without reading or writing anything, and the mark stays. It reads first; then the energy rows, the cost rows and both shifts are built and queued with no await between them, so a cancellation (the dialog closed, a time limit, a reload) comes either before them, and nothing is written, or after them, when everything is queued: never the energy without its cost. A test checks that all of them are queued in one turn of the event loop. Time budgets are checked before requests only, never inside a replay, and do not count the time a replay takes (see the time budget, above).
5. **Confirmed.** One barrier (an empty `async_clear_statistics` with `on_done`, up to 30 s, `CONFIRM_TIMEOUT_SECONDS`), then a read-back of the joins the replay wrote, and only those: the predecessor and the first row, the last row and the first row shifted, each a step equal to the later row's state, with the first and last rows as written. On a mismatch, as for an import the recorder queued again behind the barrier, up to two more barriers. Still unconfirmed, the replay raises `StatisticsWriteError`, its lock is released, and its unit fails with `statistics_write`. The measurement cache, the frontier and the record of a finished initial import move on only once a replay is confirmed, so the next sync offers the same rows from the same hour, and its replay heals what the recorder saved in part. A replay that reached back more than 14 days, as an initial import or one after a long outage, starts at its walk's cutoff instead, which the retry works out from its own time, later; and a new coordinator, as after a failed setup attempt or a reload, reads the frontier from the recorder, which usage saved without its cost has moved on, so its walk would not reach back that far either. So the coordinator remembers the oldest hour such a replay wrote (`_note_unconfirmed`), as it does when the sync is cancelled while that replay runs, as by an unload of its entry, which leaves its writes queued, and every walk of the unit, whatever its mode, reaches back to it (`_requested_since`) until a replay from it is confirmed by a walk that fetched every window. It keeps the hour in a mapping its owner passes it (`unconfirmed`): the setup flow keeps it across its attempts, for the units whose statistics its rollback leaves, setup hands it to the entry with the rest of its memory (`SyncMemory.unconfirmed`), and the entry keeps it across its reloads, the user's and those that reauthentication and reconfiguration make (`hass.data[DOMAIN]["unconfirmed_replays"]`, keyed by the entry's ID and dropped when the entry is removed). Otherwise, when the recorder saved one statistic and dropped the other, the hours between the two cutoffs would keep their usage without its cost, or the reverse, for good. The hour is kept in memory only, so a restart of Home Assistant before a confirmed retry forgets it, and the hours between the two cutoffs can then stay half saved for good: from the recorder alone, a restart cannot tell usage stored without its cost from hours whose cost Meridian has not published. A lane's coverage or revision window that was not confirmed, or whose import an unload of its entry cancelled, fails nothing: its dates wait, then are replayed in full, a day at a time (see Lanes), and the entry keeps them across its reloads in the same way (`hass.data[DOMAIN]["unsaved_coverage"]`, keyed by the entry's ID and dropped when the entry is removed), as the recorder may have saved their rows without the shift of the rows after them; a restart forgets them, which can leave that seam for good.

Seams left by releases before 0.3.0 are not searched for, and not repaired at start-up: a downward manual correction is a negative step too, and a repair would undo it. A seam inside a span a replay writes is rewritten with the span, as in the 14 days that every restart, reload and weekly reconciliation replay; older ones stay. Rolling back to an earlier 3.x release keeps the sums consistent: it reads the same hourly rows and continues them from the newest stored row before its window.

Current-bill totals are summed from the changes of the stored hourly rows for the billing period, read after a barrier of up to 30 s (until 0.3.0 an unbounded wait for the recorder), and are reported only when those rows cover every hour from the start of the period, and each of them steps from the one before by its own state: usage and export as well as cost and credit, so a stale running sum, as a seam an earlier release left, is never reported as a total. That leaves a total unknown for the period too where a user adjusted its running total, and a cost or credit with the usage or export it goes with. Missing cost is never treated as zero. All recorder writes and deletes go through the public Recorder API on the recorder's own thread (`async_add_external_statistics`, `async_adjust_statistics`, `async_clear_statistics`); tests cover this against a real recorder (`recorder_mock`), and check the prefix sums of energy and cost after every sync path (`tests/test_statistics_replay.py`, `tests/test_replay_recorder.py`).

## Entities

- **Last data update**, **Latest usage data**: timestamps (diagnostic).
- **Provisional data intervals**: count of non-actual intervals in the correction window (`state_class: measurement`).
- **Current bill usage / cost / export / export credit**: bill-to-date totals computed from the statistics for the current billing period, with the period dates and a completeness flag as attributes. They have no state class: Home Assistant keeps no long-term statistics for them and does not offer them in the Energy dashboard, because the external statistics are the long-term record.
- **Billing period start / end**, **Next billing date**: dates, disabled by default.

Feed-in sensors are created only for accounts with feed-in metering and removed when that stops. Devices for accounts that are no longer selected are detached.

## Config entries

Entries are version 3, minor version 1. `async_migrate_entry` promotes completed 3.0 entries (from 0.2.4) to 3.1, raises a translated `ConfigEntryError` for anything it cannot use, and accepts a higher 3.x minor version unchanged so that rolling back to an earlier release still loads the entry. A future change that earlier 3.x releases cannot read needs a major-version bump.

## Privacy

- Diagnostics contain versions, counts, flags, timestamps and timings; never emails, account or meter numbers, ICPs, addresses, tokens, usage or cost. A lane's coverage appears as two booleans (`reaches_target`, `history_start_found`), never as a number of history days. Each unit appears by its account's and property's positions (`1/2`) and its direction, with its status (`pending`, `ok`, `failed` or `degraded`), the reconciliation it owes, the seconds until it is tried again (none until a first sync has succeeded, since every attempt until then tries each unit, the first after setup included), how many updates in a row ran out of time before its first request (`not_reached`), and its last failure's reason, error class, HTTP status and age in seconds (`unit_diagnostics`).
- Logs never include payloads, headers or identifiers.
- At debug level the transport logs every answer once its body is read and before it is parsed: the operation, status, content class, byte length, the hop that wrote an error page (`cloudflare`, `awselb`, `nginx` or `other`, from fixed body markers only), whether a `cf-ray` header was present, and the time taken. A timeout or network failure logs its class and the time taken and, when the status and headers had arrived before the body failed, the status, content class, `cf_ray` and the time to the headers. The transport raises network errors as its own errors, which name the library's error class but not its text: that text can hold the URL, so a traceback never shows it. When the status that had arrived was unsuccessful (400 or more), the status is the answer: the transport raises it as a `MeridianHttpError` with an empty payload, as for a complete error page, whose `error_class` names the network error. So a gateway's 504 whose page was cut off or stalled is still `upstream_timeout` with `HTTP 504`, a 503's is `upstream_unavailable`, and a 429's `Retry-After` still applies; the failure WARNING gives the status and names the network error as `root=`. A successful status whose body failed stays a network error or a timeout. The coordinator logs each measurements page (mode, direction, account and property positions, window `k/n`, page, the window's dates as NZ days from today such as `bounds=-13d..-7d`, whether it sent `before`, page size, rows received, rows kept (each hour and channel once, on the first page that had it, so a second reading for an hour already kept is not counted and the pages' counts add up to the rows the fetch kept), rows before the window, whether the window's first hour (00:00 on `startOn`) and last hour (23:00 on `endOn`) have come back in any of its pages so far, the oldest and newest row as whole hours from the current hour, whether more pages exist, time taken) and each failed page (its class, HTTP status and what happens next: `retry`, `probe_1d`, `split_1d` or `stop`). An empty window older than every reading the walk returned logs no page line, because it would show when the history starts; the sync summary says `history_start=yes`, with counts of windows that returned readings, came back empty or failed, of resent requests, and of windows asked for again by their days (`splits`): after a failure in the same sync, or because of the probe or the days an earlier hourly update left it (`_UnitWalk.splits`), but not a window asked for by day only because the walk keeps days for the rest of the sync. URLs, headers, bodies, cursors, variables, identifiers and dates are never logged, tracebacks included; `tests/test_privacy_logs.py` checks this end to end against a synthetic Meridian service at the HTTP level, including the exception messages in each traceback, every cursor the service issued and its encoded form, and real aiohttp errors whose text holds the URL.
- Account selection labels show an address and the last four digits of the account number locally in the Home Assistant UI only.
- A snapshot test (`tests/snapshots/test_sensor_diagnostics.ambr`) holds the full diagnostics payload, so any new field shows up in review.
